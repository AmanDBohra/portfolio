Qlik Sense Data Architect (QSDA 2024) — Study Guide

Data modeling and scripting in Qlik Sense: load scripts, joins/concatenation/mapping, QVDs and incremental load, resolving synthetic keys and circular references, star-schema modeling, and Section Access.

~50 questions · 120 minutes · scenario-based on data loading and modeling · passing per Qlik scoring.

What it is

The Qlik Sense Data Architect (QSDA) validates the ability to design and build the data layer of Qlik Sense apps: load scripting, the associative data model, joins/concatenation/mapping, QVDs and incremental loading, resolving synthetic keys and circular references, star-schema modeling, and Section Access security.

It focuses on the 'behind the scenes' engineering that makes Qlik apps fast and correct — clean data models, efficient QVD layers, and governed, secure data.

Where it's used

  • Roles: Qlik Data Architect, BI Developer, Data Modeler working with Qlik.
  • On the job: building reload scripts and QVD layers, designing performant associative models, and implementing incremental loads and row-level security.
  • Career value: validates the technical foundation of Qlik solutions, distinguishing app builders who can engineer robust data models.
  • For this portfolio: underpins years of Qlik-based BI delivery and the data models behind executive dashboards.

In plain English

  • Qlik links tables automatically by matching column NAMES — like two forms that both have 'CustomerID' snap together. So naming your columns IS your data model.
  • A QVD is Qlik's tupperware: pre-portioned, sealed data that loads super fast next time — the basis of quick reloads and incremental loading.
  • A synthetic key is what Qlik makes when two tables accidentally share two+ column names — usually a mess you want to clean up by renaming or combining keys.
  • Incremental load is only cooking the new orders and adding them to yesterday's batch, instead of re-cooking the whole week every night.

Exam shortcut tricks

  1. Synthetic key = 2+ shared fields between tables. Fix by renaming, dropping, or making ONE composite key. Circular reference = a loop; fix with a link table.
  2. CONCATENATE = stack rows (union). JOIN = merge columns (can multiply rows). ApplyMap = add ONE lookup value with NO row duplication (often the best answer).
  3. Optimized QVD load = fastest; ANY transformation/WHERE breaks it — except a single WHERE EXISTS(field). That exception is a common exam point.
  4. Association is by identical field names — this is THE core Qlik concept behind most modeling questions.
  5. Section Access = row-level security; fields conventionally UPPERCASE; always keep a valid admin or you lock yourself out.
  6. Star schema / link table beats many shared fields — avoids synthetic keys and keeps performance up.
  7. AutoNumber() shrinks big composite/text keys into small integers — the answer for memory/performance on large keys.

Study roadmap

  1. Data connections & loading — LOAD statements, resident loads, and connecting to files/databases.
  2. Associative model — how Qlik associates tables by identically named fields (no explicit joins needed at UI level).
  3. Data model issues — synthetic keys (multiple shared fields) and circular references; how to detect and resolve.
  4. Combining tables — JOIN (inner/left/right/outer), CONCATENATE, Keep, and Mapping (ApplyMap) — and when to use each.
  5. QVDs — creating/reading QVD files, optimized vs unoptimized loads, and incremental load patterns.
  6. Star schema & link tables — modeling multiple fact tables cleanly.
  7. Section Access — data reduction and security by user.
  8. Best practices — key handling, naming, and performance (optimized QVD loads).

Study notes

Associative model & keys

  • Qlik associates tables automatically on fields with the same name — so field naming is the data model.
  • A synthetic key is created when two or more tables share two or more fields; usually undesirable — resolve by renaming, removing, or creating a composite key.
  • A circular reference occurs when tables form a loop of associations; break it by renaming fields or using a link table.

Combining tables

  • CONCATENATE stacks rows (union) — implicit when two loaded tables have identical field sets.
  • JOIN merges columns on common fields (can multiply rows); use deliberately.
  • ApplyMap (with a mapping table) is often preferred over JOIN for adding a single lookup value — faster and no row duplication.

QVD & incremental load

  • QVD = Qlik's optimized binary file for fast reads and staging.
  • Optimized load (no transformations/WHERE on non-indexed fields) is far faster than unoptimized.
  • Incremental load: load only new/changed records from source, then concatenate with existing QVD (using max modified timestamp / WHERE NOT EXISTS).

Section Access

  • Section Access secures data by user, reducing what each user can see (row-level security).
  • Fields are typically uppercase; reductions match the logged-in user to allowed values.

Hands-on projects

1. Associative insurance data model

Goal: Build a clean, synthetic-key-free model for policy/claims/distributor data.

Architecture & data model: Sources loaded and validated in the model viewer; keys named deliberately; a link table connects multiple facts to shared dimensions.

Concepts covered:

  • Associative model: Qlik links tables by identical field names; naming is effectively the data model.
  • Synthetic keys: Auto-created when tables share 2+ fields; usually resolved to keep the model clean.
  • Circular references: Association loops causing ambiguity; broken via renaming or a link table.
  • Star schema / link table: A central fact + dimensions (or a link table for multi-fact) avoids synthetic keys/loops.
  • Key naming: Deliberate key names (e.g., %CustomerKey) ensure only intended tables associate.

Implementation steps:

  1. Load sources; inspect for synthetic keys/loops.
  2. Rename/qualify coincidental fields; build composite keys where needed.
  3. Introduce a link table for shared dimensions.
  4. Validate associations in the data model viewer.

Outcomes:

  • Clean, synthetic-key-free model.
  • Unambiguous associations.
  • Fast, correct dashboards.

2. QVD staging & incremental load

Goal: Speed reloads by staging to QVDs and loading only new/changed rows.

Architecture & data model: Sources → extract QVDs → incremental logic (max modified date variable) → concatenate + STORE back to QVD → app loads optimized QVDs.

Concepts covered:

  • QVD (optimized load): Qlik's binary staging format; optimized loads stream directly into memory, very fast.
  • Incremental load: Fetch only new/changed rows and combine with the stored QVD.
  • WHERE NOT EXISTS: Loads only keys not already present, avoiding duplicates on append.
  • STORE/LOAD: STORE writes in-memory tables to QVD; LOAD reads them back (optimized).
  • Handling updates/deletes: Update by taking fresh rows + WHERE NOT EXISTS; reconcile deletes against current keys.

Implementation steps:

  1. Extract sources to QVDs; capture last max modified date in a variable.
  2. Load newer rows; concatenate retained rows WHERE NOT EXISTS(key).
  3. Reconcile deletes against current source keys.
  4. Keep optimized loads (single WHERE EXISTS exception).

Outcomes:

  • Fast, incremental reloads.
  • No duplicates on append.
  • Reduced source load.

Stack: Qlik Sense, QVD, Load script

Incremental QVD architecture is standard for large enterprise reloads.

3. Transformations: joins, mapping & crosstables

Goal: Shape messy source data into an analytics-ready model.

Architecture & data model: Messy sources shaped via ApplyMap, preceding loads, crosstable, subfield, and IntervalMatch into an analytics-ready model.

Concepts covered:

  • JOIN vs CONCATENATE vs KEEP: JOIN merges columns (can multiply rows); CONCATENATE unions rows; KEEP reduces but keeps tables separate.
  • ApplyMap (mapping load): Key-based single-value lookup that never duplicates rows — often better than JOIN.
  • Preceding load: Transform a load's output in one pass without a resident second pass.
  • Crosstable/Generic load: Crosstable pivots wide data to long; Generic turns attribute rows into columns.
  • Subfield/IntervalMatch: Subfield splits delimited values; IntervalMatch maps values to ranges.

Implementation steps:

  1. Use ApplyMap for single-value lookups (no duplication).
  2. Concatenate multi-source facts with a source flag; JOIN only where safe.
  3. Pivot wide data with CROSSTABLE; split multi-values with Subfield.
  4. Bucket ranges (age bands) with IntervalMatch.

Outcomes:

  • Clean model from imperfect sources.
  • No accidental row explosion.
  • Reusable transform patterns.

4. Master calendar & performance tuning

Goal: Add a gap-free calendar and optimize memory/reload.

Architecture & data model: A generated master calendar + reduced-cardinality keys + precomputed flags feed lean, fast charts.

Concepts covered:

  • Master calendar generation: A gap-free date table with Year/Quarter/Month for reliable time analysis.
  • Cardinality reduction (split datetime): Splitting timestamps into Date + Time cuts distinct values and memory.
  • AutoNumber keys: Compresses composite/text keys into small integers.
  • Optimized QVD loads: Avoid transformations on QVD reads to keep them fast.
  • Precomputed flags: Compute flags in the script so charts don't recompute per interaction.

Implementation steps:

  1. Generate a continuous date table with derived fields.
  2. Split timestamps into Date + Time.
  3. AutoNumber large composite keys.
  4. Precompute flags in the script.

Outcomes:

  • Reliable time analysis.
  • Lower memory footprint.
  • Faster chart rendering.

Stack: Qlik Sense, Load script

Performance and clean time analysis are hallmarks of good Qlik delivery.

5. Section Access data security

Goal: Restrict each user to their permitted rows (e.g., region).

Architecture & data model: A Section Access table maps authenticated users to permitted regions; data reduces per user; tested in a copy before release.

Concepts covered:

  • Section Access: User-based data reduction (row-level security) defined in the script.
  • Data reduction: Each user sees only rows matching their permitted values.
  • Reduction fields (UPPERCASE): Matching is case-sensitive; conventionally uppercase for reliability.
  • Admin vs user access: ADMIN sees all; USER is reduced — always keep a valid admin.
  • Testing safely: Test in a copy to avoid locking yourself out.

Implementation steps:

  1. Build the Section Access table (user → region).
  2. Use uppercase fields/values; keep a valid admin.
  3. Reduce data by matching the logged-in user.
  4. Test in a copy to avoid lockout.

Outcomes:

  • Row-level security per user.
  • Safe, reliable matching.
  • No lockout risk.

Stack: Qlik Sense, Section Access

Row-level security is essential on sensitive insurance data.

Practice questions (100)

1. In Qlik, how are two tables associated?

  • A. By explicit JOIN keys defined in the UI
  • B. Automatically on fields that share the same name ✓
  • C. By row order
  • D. They cannot be associated

Explanation: Qlik's associative engine links tables automatically through fields that have identical names. This means field naming effectively defines the data model — a core concept for the QSDA exam.

2. What causes a synthetic key?

  • A. A single shared field between two tables
  • B. Two or more tables sharing two or more fields in common ✓
  • C. Loading a QVD
  • D. Using ApplyMap

Explanation: A synthetic key is auto-generated when two (or more) tables share two or more fields. It's usually undesirable; resolve by renaming fields, removing redundant ones, or building an explicit composite key.

3. Which approach is generally preferred to add a single lookup value without duplicating rows?

  • A. JOIN
  • B. CONCATENATE
  • C. ApplyMap with a mapping table ✓
  • D. CROSS TABLE

Explanation: ApplyMap uses a mapping table to look up a value key-by-key — it never multiplies rows and is typically faster than a JOIN for adding one field. JOIN can unintentionally duplicate rows if the key isn't unique.

4. What is the benefit of an 'optimized' QVD load?

  • A. It applies more transformations
  • B. It reads the QVD directly into memory with minimal processing, making it much faster ✓
  • C. It encrypts the data
  • D. It resolves synthetic keys automatically

Explanation: An optimized QVD load happens when data is read essentially as-is (no transformations, no WHERE on non-indexed fields). Qlik streams it into memory very quickly. Adding transformations breaks optimization (unoptimized, slower).

5. A circular reference in a Qlik data model is best resolved by:

  • A. Deleting all tables
  • B. Renaming fields to break the loop or introducing a link table ✓
  • C. Adding more synthetic keys
  • D. Using CONCATENATE

Explanation: Circular references (a loop of associations) create ambiguity. Resolve by renaming/qualifying fields to break the loop or by restructuring with a link table so associations are unambiguous.

6. Which statement stacks rows from two tables with the same fields into one table?

  • A. JOIN
  • B. CONCATENATE ✓
  • C. KEEP
  • D. MAPPING LOAD

Explanation: CONCATENATE appends the rows of one table to another (a union). Qlik even does this implicitly (auto-concatenate) when two loaded tables have identical field sets.

7. In an incremental load, how do you typically load only new or changed records?

  • A. Reload everything each time
  • B. Filter the source by a modification timestamp greater than the last load, then concatenate with the existing QVD ✓
  • C. Use Section Access
  • D. Use a pie chart

Explanation: Incremental load queries the source for records changed since the last run (e.g., WHERE ModifiedDate >= last max), then concatenates with the stored QVD (handling updates/deletes as needed) — minimizing load time.

8. What does Section Access provide?

  • A. Faster chart rendering
  • B. User-based data reduction / row-level security ✓
  • C. Automatic joins
  • D. QVD compression

Explanation: Section Access controls which data each user can see by matching the authenticated user to permitted field values, reducing the dataset per user — Qlik's row-level security mechanism.

9. A 'resident' load in Qlik script means loading from:

  • A. An external database
  • B. A table already loaded in memory during the same script ✓
  • C. A QVD file only
  • D. A web API

Explanation: LOAD ... RESIDENT <table> reads from a table already in memory (loaded earlier in the script), useful for further transformation, aggregation, or ordering without re-reading the source.

10. Which is a valid reason to use a link table in a multi-fact model?

  • A. To create synthetic keys intentionally
  • B. To connect multiple fact tables to shared dimensions without circular references or synthetic keys ✓
  • C. To encrypt the model
  • D. To replace QVDs

Explanation: A link table consolidates the shared key combinations from multiple fact tables so they associate to common dimensions cleanly — avoiding synthetic keys and circular references in multi-fact models.

11. The AutoNumber() function is used to:

  • A. Generate random data
  • B. Replace composite/text keys with compact integer keys to save memory ✓
  • C. Sort a table
  • D. Create a QVD

Explanation: AutoNumber() converts key values (often composite/hashed) into sequential integers, reducing memory footprint and improving association performance for large key fields.

12. A Mapping load table used with ApplyMap must have:

  • A. Any number of columns
  • B. Exactly two columns: the lookup key and the return value ✓
  • C. At least three columns
  • D. A synthetic key

Explanation: MAPPING LOAD tables must have exactly two fields — the first is matched against the lookup value and the second is returned by ApplyMap. Extra columns are ignored/invalid.

13. The Qualify statement in a load script:

  • A. Removes duplicates
  • B. Prefixes field names with the table name to avoid unwanted associations ✓
  • C. Creates a QVD
  • D. Applies Section Access

Explanation: QUALIFY prefixes fields with their table name (Table.Field), preventing unintended automatic associations on same-named fields — useful to avoid synthetic keys during development.

14. Which prefix loads records only if the key does not already exist, useful in incremental loads?

  • A. WHERE EXISTS
  • B. WHERE NOT EXISTS(KeyField) ✓
  • C. DISTINCT
  • D. GROUP BY

Explanation: WHERE NOT EXISTS(KeyField) loads only rows whose key isn't already present in the in-memory field — a common pattern to append new records during incremental loads without duplicates.

15. A Preceding Load lets you:

  • A. Load from a QVD only
  • B. Apply further transformations on top of a load without a resident/second pass ✓
  • C. Create Section Access
  • D. Concatenate two files

Explanation: A preceding load stacks a LOAD on top of another LOAD/SELECT, transforming its output in one pass (no separate resident load) — efficient for adding calculated fields.

16. The Concatenate prefix is needed when:

  • A. Two tables have identical fields (auto-concatenation already happens)
  • B. You want to force two tables with differing fields to append into one table ✓
  • C. You load a QVD
  • D. You apply a map

Explanation: Qlik auto-concatenates tables with identical field sets. Use the explicit CONCATENATE prefix to force appending when field sets differ (missing fields become null).

17. A star schema in Qlik is preferable to a fully normalized model because:

  • A. It always uses less disk
  • B. Fewer table hops and no synthetic keys improve performance and simplicity ✓
  • C. It disables associations
  • D. It is required for QVDs

Explanation: A star schema (central fact + dimensions) reduces association complexity and avoids synthetic keys/circular references, giving better in-memory performance and a cleaner model than deep snowflakes.

18. Section Access with 'STRICT EXCLUSION' means:

  • A. All users see all data
  • B. Users with no matching reduction value are denied access to data ✓
  • C. Fields must be lowercase
  • D. QVDs are encrypted

Explanation: Strict exclusion enforces that if a user has no matching value in the reduction field, they are excluded from that data (rather than seeing everything) — a secure default for row-level security.

19. The Peek() function in a script:

  • A. Loads a QVD
  • B. Retrieves a value from a specific row/field of a table already in memory ✓
  • C. Creates a synthetic key
  • D. Removes duplicates

Explanation: Peek('Field', row, 'Table') reads a value at a given row of an already-loaded table — commonly used in incremental logic (e.g., reading the last loaded max date) and running calculations.

20. Which is TRUE about storing to a QVD with STORE?

  • A. It can only store to CSV
  • B. STORE Table INTO file.qvd (qvd) writes the in-memory table to a QVD for reuse ✓
  • C. It deletes the table
  • D. It creates Section Access

Explanation: STORE writes an in-memory table to disk as a QVD (or CSV/txt). QVDs are then reused across apps and enable incremental-load staging.

21. An IntervalMatch is used to:

  • A. Match discrete values to ranges (e.g., a date to a start/end interval) ✓
  • B. Concatenate tables
  • C. Apply a map
  • D. Create a QVD

Explanation: IntervalMatch associates a discrete value (like a date or number) with ranges defined by start/end fields — useful for slowly changing dimensions and bucketing into bands.

22. To break a circular reference without renaming source fields, a common structural fix is:

  • A. Add a synthetic key
  • B. Build a link table ✓
  • C. Use DISTINCT
  • D. Increase RAM

Explanation: A link table consolidates the shared keys from the tables in the loop into one bridge table, removing the circular path and letting dimensions associate unambiguously.

23. Which is the best reason to use an incremental load rather than a full reload?

  • A. To always reload everything
  • B. To reduce reload time and source load by only processing new/changed data ✓
  • C. To create synthetic keys
  • D. To disable Section Access

Explanation: Incremental loads fetch only new/changed records and combine them with stored QVDs, cutting reload duration and source system load — essential for large, frequently-updated datasets.

24. The Subfield() function is used to:

  • A. Join tables
  • B. Split a delimited string into parts (optionally generating multiple rows) ✓
  • C. Create a QVD
  • D. Apply Section Access

Explanation: Subfield(text, delimiter [, n]) extracts the nth part of a delimited string, or without n generates a row per part — handy for normalizing multi-value fields.

25. A Crosstable load prefix is used to:

  • A. Pivot cross-tab (wide) data into a long/normalized form ✓
  • B. Create Section Access
  • C. Compress QVDs
  • D. Join two tables

Explanation: CROSSTABLE transforms a wide table (many value columns, e.g., months across columns) into a normalized long format with an attribute field and a data field.

26. Which is TRUE about how Qlik handles a field that exists in three tables?

  • A. It creates three copies
  • B. It associates all three tables on that field (potential for unintended links) ✓
  • C. It ignores the field
  • D. It errors out

Explanation: A single common field associates all tables sharing it. If that link is unintended it can distort the model, so architects rename/qualify fields to control associations.

27. Storing to QVD then loading FROM it 'optimized' is broken by:

  • A. Loading all fields as-is
  • B. Adding a WHERE on a non-EXISTS condition or transforming fields ✓
  • C. Using STORE
  • D. Renaming the QVD

Explanation: Optimized QVD loads permit essentially no transformation (one WHERE EXISTS on a single field is allowed). Other WHEREs, new/derived fields, or transformations force an unoptimized load.

28. The NoConcatenate prefix is needed when:

  • A. You want to force-append two tables
  • B. Two tables have identical fields but you want to keep them separate (prevent auto-concatenation) ✓
  • C. Loading a QVD
  • D. Creating Section Access

Explanation: When two loaded tables share the exact same field set, Qlik auto-concatenates them. NoConcatenate forces Qlik to keep them as separate tables.

29. Which function generates a hash to build a compact composite key?

  • A. Hash128()/Hash256() or AutoNumberHash ✓
  • B. Peek()
  • C. Subfield()
  • D. ApplyMap()

Explanation: Hash128/Hash256 (often combined with AutoNumberHash) produce a single key value from multiple fields, replacing multi-field composite keys and avoiding synthetic keys efficiently.

30. A generic load is used to:

  • A. Load generic files
  • B. Transform attribute/value rows into separate fields/columns ✓
  • C. Create Section Access
  • D. Compress data

Explanation: GENERIC LOAD converts a table of entity/attribute/value rows into a wide structure with one column per attribute — the inverse of a crosstable in effect.

31. When incremental data includes deletes, a robust pattern is to:

  • A. Ignore deletes
  • B. Compare against a list of current keys from source and remove missing keys via WHERE EXISTS/inner keep ✓
  • C. Reload everything (only option)
  • D. Use Section Access

Explanation: Handling deletes typically means reconciling stored data against the source's current key set (e.g., inner keep on current keys) so removed records are dropped from the QVD.

32. The LOAD ... FROM ... (qvd) with an optimized read is fastest because Qlik:

  • A. Recompresses the data
  • B. Reads the pre-built symbol tables/structures directly into memory ✓
  • C. Applies transformations
  • D. Rebuilds associations from scratch

Explanation: QVDs store Qlik's internal representation, so an optimized load streams those structures straight into memory with minimal processing — the fastest load path.

33. A best practice to avoid ambiguous associations in a complex model is to:

  • A. Share as many field names as possible
  • B. Deliberately name key fields and rename descriptive fields that shouldn't link ✓
  • C. Never use QVDs
  • D. Disable Section Access

Explanation: Intentional field naming — matching only true keys and renaming coincidentally-shared descriptive fields — keeps the associative model clean and prevents synthetic keys/unwanted links.

34. The Exists() function in a WHERE clause checks whether:

  • A. A file exists
  • B. A value already exists in a previously loaded field (for filtering/incremental logic) ✓
  • C. A QVD exists
  • D. A chart exists

Explanation: Exists(Field [,value]) tests whether a value is already present in a loaded field — used for incremental filtering (WHERE NOT EXISTS) and validation.

35. Which statement about link tables and memory is TRUE?

  • A. They always increase memory drastically
  • B. They can add a bridge table but remove synthetic keys, often improving clarity/performance ✓
  • C. They replace QVDs
  • D. They disable associations

Explanation: A link table introduces one bridge table but eliminates synthetic keys/circular references, usually yielding a cleaner, well-performing multi-fact model.

36. To parameterize file paths or reuse logic in scripts, Qlik provides:

  • A. Variables (SET/LET) and subroutines (SUB/CALL) ✓
  • B. Only hard-coded paths
  • C. Bookmarks
  • D. Section Access

Explanation: SET/LET define variables and SUB/CALL define reusable subroutines, enabling parameterized, maintainable load scripts (e.g., a variable base path used across loads).

37. The ApplyMap third argument (default value) specifies:

  • A. The delimiter
  • B. What to return when the key isn't found in the mapping table ✓
  • C. The table name
  • D. A QVD path

Explanation: ApplyMap('Map', key, defaultValue) returns defaultValue when the lookup key has no match — preventing nulls and controlling unmatched behavior.

38. The 'Loosely coupled' state can be set intentionally to:

  • A. Improve associations
  • B. Break a specific association (e.g., resolve a loop) at the model level ✓
  • C. Create QVDs
  • D. Encrypt fields

Explanation: Marking a table loosely coupled severs its association, which can deliberately break a circular reference — though a link-table restructure is usually cleaner.

39. Which is the correct way to load only distinct rows?

  • A. LOAD DISTINCT ... ✓
  • B. WHERE UNIQUE
  • C. GROUP DISTINCT
  • D. SELECT ONLY

Explanation: LOAD DISTINCT removes duplicate rows during load. It's useful when a source produces repeated records you don't want duplicated in the model.

40. The RowNo() and RecNo() functions differ in that RowNo():

  • A. Counts source records; RowNo counts output rows of the resulting table ✓
  • B. They are identical
  • C. Only works on QVDs
  • D. Returns dates

Explanation: RecNo() returns the record number in the current input source, while RowNo() returns the row number in the resulting in-memory table (after filters/concatenation).

41. Which is a benefit of splitting a datetime into Date and Time fields?

  • A. Higher cardinality
  • B. Lower cardinality and memory, plus cleaner date associations ✓
  • C. Encryption
  • D. Section Access

Explanation: A full timestamp has huge distinct-value cardinality. Splitting into Date (and optionally Time) reduces memory and enables clean associations to a calendar/master dimension.

42. A Master Calendar is typically built to:

  • A. Store Section Access
  • B. Provide a continuous date dimension with Year/Quarter/Month fields for time analysis ✓
  • C. Compress QVDs
  • D. Replace ApplyMap

Explanation: A master calendar generates a gap-free date table with derived fields (Year, Month, Week), enabling reliable time-series analysis and avoiding missing-date gaps.

43. The Where clause with Exists during an optimized QVD load is special because:

  • A. It always breaks optimization
  • B. A single WHERE EXISTS(field) can keep the load optimized ✓
  • C. It requires two fields
  • D. It encrypts data

Explanation: Optimized QVD loads normally break with any WHERE, but a single WHERE EXISTS(field) is the allowed exception that preserves optimization — useful in incremental patterns.

44. Interval matching with the extended (IntervalMatch with key) syntax handles:

  • A. Only single dates
  • B. Overlapping intervals and additional key fields ✓
  • C. QVD creation
  • D. Section Access

Explanation: The extended IntervalMatch (with keys) supports matching where intervals overlap or where an extra key must also match — more flexible than the basic form.

45. To handle a source with inconsistent date formats, you would use:

  • A. Date#() to interpret, then Date() to format ✓
  • B. ApplyMap only
  • C. Section Access
  • D. STORE

Explanation: Date#(string, format) interprets a text date using an explicit format; wrapping with Date() then displays it consistently — the standard way to normalize messy dates.

46. Which reduces reload dependency on a slow source system?

  • A. Full reload every time
  • B. Extract to QVD on a schedule, then build the app from QVDs ✓
  • C. Add synthetic keys
  • D. Disable QVDs

Explanation: Decoupling with a QVD extract layer means the app loads from fast local QVDs rather than repeatedly hitting the slow source, improving reliability and speed.

47. The Concatenate vs Join decision for two large fact tables usually favors:

  • A. JOIN (to multiply rows)
  • B. CONCATENATE (or a link table) to avoid row explosion and synthetic keys ✓
  • C. ApplyMap
  • D. Section Access

Explanation: Joining two facts can explode rows and create bad grain. Concatenating (with a source flag) or using a link table keeps the model correct and performant.

48. Which function returns the number of the current iteration in a loop (e.g., FOR)?

  • A. The loop variable itself ✓
  • B. Peek()
  • C. Subfield()
  • D. ApplyMap()

49. To document/label a table's origin for debugging, an architect may add:

  • A. A source flag field (e.g., 'Source' = 'CRM') during load ✓
  • B. A synthetic key
  • C. Section Access
  • D. A gauge

Explanation: Adding a literal source/flag field during each load aids lineage and lets concatenated facts be distinguished and filtered later.

50. Which is TRUE about the QVD 'creation' vs 'source' file time in incremental logic?
