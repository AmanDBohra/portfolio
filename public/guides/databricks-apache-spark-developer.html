Databricks Certified Associate Developer for Apache Spark — Study Guide

Apache Spark architecture and the DataFrame API: transformations vs actions, selecting/filtering/joining/aggregating data, partitioning, caching, and how Spark plans and executes jobs.

~60 questions · 120 minutes · code-focused (Python or Scala DataFrame API) · passing ~70%.

What it is

The Databricks Certified Associate Developer for Apache Spark validates hands-on proficiency with Spark's architecture and the DataFrame API. It tests how Spark executes work (driver/executors, jobs → stages → tasks, partitions), the difference between lazy transformations and actions, narrow vs wide operations and shuffles, joins, aggregations, window functions, caching, partitioning, and performance features like broadcast joins and Adaptive Query Execution.

It is a code-level, engine-focused certification: it proves you can read Spark code, predict how it runs, and write efficient transformations rather than just use higher-level tools.

Where it's used

  • Roles: Spark/Data Engineer, Big Data Developer, ML Engineer working with large datasets.
  • On the job: writing performant PySpark/Scala transformations, diagnosing shuffles and skew in the Spark UI, and optimizing large-scale ETL and feature pipelines.
  • Career value: Spark remains the backbone of large-scale data processing; this cert demonstrates the engine fundamentals that underpin Databricks, EMR, and other Spark platforms.
  • For this portfolio: supports the data-engineering and big-data processing behind enterprise analytics and data-science workloads.

In plain English

  • Spark is a team of chefs (executors) with one head chef (driver). The head chef plans the menu and hands out tasks; the chefs cook in parallel. You (the code) just describe the dish.
  • Transformations are writing a recipe; nothing cooks until you say 'serve it' (an action like count/collect/write). That's 'lazy evaluation'.
  • A shuffle is everyone swapping ingredients across the kitchen so all the tomatoes end up at one station — expensive. Narrow steps (chop your own veg) need no swapping; wide steps (group by) do.
  • A broadcast join is photocopying a tiny recipe card for every chef instead of making everyone line up at one printer — avoids the big line (shuffle).

Exam shortcut tricks

  1. Action vs transformation: if it RETURNS a result to you (count, collect, show, take, write) it's an action and triggers execution. Everything else is lazy.
  2. Wide = shuffle = new stage: groupBy, join, distinct, repartition, orderBy. Narrow = no shuffle: select, filter, map, withColumn.
  3. repartition = full shuffle, up OR down, balanced. coalesce = no full shuffle, DOWN only. 'Reduce partitions cheaply' = coalesce.
  4. One partition = one task. Job → Stage(s) at shuffles → Task(s) per partition. Memorize this hierarchy.
  5. Small table in a join? Broadcast it. Skewed key? Salt it or let AQE handle skew.
  6. Avoid collect()/toPandas() on big data (driver OOM). Use count/take/show or write out.
  7. Python UDFs are slow (serialization, no Catalyst). Prefer built-in functions; the 'why is this slow' answer is often 'it's a UDF.'

Study roadmap

  1. Spark architecture — driver vs executors, cluster manager, and the unit hierarchy: job → stage → task; partitions map to tasks.
  2. Transformations vs actions — lazy transformations (select, filter, join, groupBy) build a plan; actions (count, collect, write, show) trigger execution.
  3. Narrow vs wide transformations — narrow (map, filter) need no shuffle; wide (groupBy, join, repartition) shuffle data across partitions and create stage boundaries.
  4. DataFrame API — column expressions, filtering, withColumn, joins (inner/left/outer/semi/anti), aggregations, window functions.
  5. Partitioning & shuffles — repartition (full shuffle, can increase) vs coalesce (no full shuffle, decrease only); spark.sql.shuffle.partitions.
  6. Caching & persistence — cache()/persist() storage levels and when caching helps or hurts.
  7. Performance — broadcast joins for small tables, Adaptive Query Execution (AQE), and predicate/column pruning.
  8. Practice reading code snippets and predicting output or fixing the API call.

Study notes

Execution model

  • The Driver builds the logical/physical plan and schedules tasks; Executors run tasks and hold cached data.
  • A job is triggered by an action; it is split into stages at shuffle boundaries; each stage runs as parallel tasks (one per partition).
  • Transformations are lazy (nothing runs until an action); this lets Spark (via Catalyst) optimize the whole plan.

Narrow vs wide

  • Narrow: each output partition depends on one input partition (map, filter, union) — no shuffle.
  • Wide: output partitions depend on many input partitions (groupBy, join, distinct, repartition) — requires a shuffle and starts a new stage.

repartition vs coalesce

  • repartition(n) does a full shuffle; can increase or decrease partitions and rebalances data evenly.
  • coalesce(n) avoids a full shuffle by merging existing partitions; only decreases partition count; can cause skew.

Joins & performance

  • Broadcast join: the small table is sent to every executor, avoiding a shuffle of the large table — use broadcast() hint for small dimensions.
  • Adaptive Query Execution (AQE) re-optimizes at runtime: coalescing shuffle partitions, switching join strategies, handling skew.

3. Shuffle & partition optimization

Goal: Cut runtime on a slow wide-transformation job.

Architecture & data model: A slow wide-transformation job profiled in the Spark UI; shuffle partitions tuned, AQE enabled, output coalesced — with before/after metrics.

Concepts covered:

  • Narrow vs wide transformations: Narrow (map/filter) need no shuffle; wide (groupBy/join) shuffle data and start new stages.

  • repartition vs coalesce: repartition = full shuffle (up/down, balanced); coalesce = no full shuffle (down only).

  1. Identify heavy shuffles/skew in the Spark UI (Shuffle Read/Write, straggler tasks).
  2. Enable AQE; adjust spark.sql.shuffle.partitions.
  3. coalesce before writing to control output files.
  4. Compare stage/task durations before and after.

Outcomes:

  • Reduced shuffle volume and runtime.
  • Balanced partitions, fewer stragglers.
  • Documented performance improvement.

4. Caching & broadcast strategy

Goal: Speed up an iterative job that reuses a base dataset and joins small lookups.

Architecture & data model: An iterative job caches a reused base DataFrame, broadcasts small lookups, and salts a skewed key — verified via the physical plan.

Concepts covered:

  • cache/persist storage levels: MEMORY_ONLY vs MEMORY_AND_DISK trade recomputation for spill; choose per reuse pattern.
  • When caching helps vs hurts: Cache datasets reused multiple times; over-caching wastes memory and causes eviction.
  • Broadcast join threshold: Tables under spark.sql.autoBroadcastJoinThreshold auto-broadcast; broadcast() forces it.
  • Skew (salting): Add randomness to hot keys to spread them across partitions and relieve stragglers.
  • Predicate/column pruning: Catalyst pushes filters and reads only needed columns to cut I/O.

Implementation steps:

  1. cache() the reused base; confirm reuse across actions.
  2. broadcast() small lookup tables in joins.
  3. Detect a skewed key; salt it or rely on AQE skew handling.
  4. Confirm pushdown/pruning in explain(); unpersist when done.

Outcomes:

  • Faster iterations via avoided recomputation.
  • Shuffle-free small-table joins.
  • Mitigated skew and reduced I/O.

  • Analytics-ready table from messy nested source.

Practice questions (100)

1. Which of the following is an ACTION (triggers execution) rather than a transformation?

  • A. select()
  • B. filter()
  • C. count() ✓
  • D. withColumn()

Explanation: count() is an action — it forces Spark to execute the plan and return a result. select, filter, and withColumn are lazy transformations that only build up the execution plan.

2. What triggers a shuffle in Spark?

  • A. A narrow transformation like filter
  • B. A wide transformation like groupBy or join ✓
  • C. Calling cache()
  • D. Reading a Parquet file

Explanation: Wide transformations (groupBy, join, distinct, repartition) require data with the same key to move to the same partition, causing a shuffle across the network — and a new stage boundary. Narrow transformations like filter/map need no data movement.

3. What is the difference between repartition(n) and coalesce(n)?

  • A. They are identical
  • B. repartition does a full shuffle and can increase or decrease partitions; coalesce avoids a full shuffle and only decreases ✓
  • C. coalesce always increases partitions
  • D. repartition only works on RDDs

Explanation: repartition(n) performs a full shuffle, rebalancing data and allowing an increase or decrease in partitions. coalesce(n) merges existing partitions without a full shuffle and can only reduce the count — cheaper but may create skew.

4. In the Spark execution hierarchy, which is the smallest unit of execution?

  • A. Job
  • B. Stage
  • C. Task ✓
  • D. Partition

Explanation: A task is the smallest unit of execution — it processes a single partition on one executor. Jobs (triggered by actions) split into stages (at shuffle boundaries), which split into tasks.

5. Why are Spark transformations described as 'lazy'?

  • A. They run on a background thread
  • B. They are not executed until an action is called, allowing whole-plan optimization ✓
  • C. They cache results automatically
  • D. They only run on the driver

Explanation: Transformations build a logical plan but don't execute until an action triggers them. Laziness lets the Catalyst optimizer analyze and optimize the entire pipeline (pruning, predicate pushdown, reordering) before any work runs.

6. Which join strategy avoids shuffling a large table by sending a small table to all executors?

  • A. Sort-merge join
  • B. Broadcast hash join ✓
  • C. Shuffle hash join
  • D. Cross join

Explanation: A broadcast hash join replicates the small table to every executor so the large table's partitions can be joined locally, avoiding an expensive shuffle. Use the broadcast() hint (or let AQE/auto-broadcast threshold apply).

7. Which component builds the execution plan and schedules tasks?

  • A. Executor
  • B. Driver ✓
  • C. Worker node
  • D. Cluster manager

Explanation: The Driver runs the main program, builds the logical and physical plans, and schedules tasks onto executors. Executors are the JVM processes that actually run tasks and store cached partitions.

8. Which return type does df.select('col') produce?

  • A. A single value
  • B. A new DataFrame ✓
  • C. A Python list
  • D. A Column object only

Explanation: select() is a transformation returning a new DataFrame with the chosen columns. DataFrames are immutable, so transformations always return a new DataFrame rather than modifying in place.

9. What does Adaptive Query Execution (AQE) do?

  • A. Encrypts shuffle data
  • B. Re-optimizes the query plan at runtime using actual statistics (e.g., coalescing shuffle partitions, handling skew) ✓
  • C. Disables the Catalyst optimizer
  • D. Forces all joins to be cross joins

Explanation: AQE uses runtime statistics to adapt the plan mid-execution — dynamically coalescing shuffle partitions, switching join strategies (e.g., to broadcast), and mitigating skewed joins — often improving performance without manual tuning.

10. Which config controls the default number of partitions created after a shuffle?

  • A. spark.executor.cores
  • B. spark.sql.shuffle.partitions ✓
  • C. spark.driver.memory
  • D. spark.default.parallelism only

Explanation: spark.sql.shuffle.partitions (default 200) sets the number of partitions produced by shuffles in the DataFrame/SQL API. Too many creates tiny tasks; too few limits parallelism — AQE can auto-coalesce them.

11. A left semi join returns:

  • A. All columns from both tables
  • B. Rows from the left table that have a match on the right, with only left columns ✓
  • C. Rows with no match on the right
  • D. The Cartesian product

Explanation: A left semi join keeps only rows from the left DataFrame that have at least one match on the right, returning just the left table's columns (like an EXISTS filter). A left anti join returns the non-matching left rows.

12. When is caching a DataFrame most beneficial?

  • A. When it is used only once
  • B. When the same DataFrame is reused multiple times in the job ✓
  • C. Always, regardless of usage
  • D. Only for streaming sources

Explanation: cache()/persist() pays off when a DataFrame is materialized once and reused several times, avoiding recomputation of its lineage. Caching something used once wastes memory and can hurt performance.

13. df.cache() is which kind of operation?

  • A. An action that runs immediately
  • B. A lazy hint — data is cached when the next action materializes it ✓
  • C. A transformation that shuffles
  • D. A no-op

Explanation: cache()/persist() mark a DataFrame to be stored, but the caching actually happens when the next action materializes it. The first action pays the cost; subsequent ones read from cache.

14. Which method returns the first n rows to the driver as a list of Row objects?

  • A. show(n)
  • B. take(n) ✓
  • C. printSchema()
  • D. explain()

Explanation: take(n) is an action returning n Row objects to the driver. show(n) prints a formatted table but returns nothing; printSchema/explain describe structure/plan without returning data.

15. What does df.explain() display?

  • A. The data
  • B. The logical and physical execution plan ✓
  • C. Cluster logs
  • D. The schema only

Explanation: explain() prints the query plan (parsed/analyzed/optimized logical and physical plans), which is essential for understanding shuffles, joins chosen, and pushdown.

16. Which join type returns rows from the left DataFrame that have NO match on the right?

  • A. left semi
  • B. left anti ✓
  • C. inner
  • D. full outer

Explanation: A left anti join keeps only left rows with no matching right row (like NOT EXISTS). A left semi join keeps left rows that DO match, returning only left columns.

17. Why can a User-Defined Function (UDF) in PySpark hurt performance?

  • A. It always crashes
  • B. It can't be optimized by Catalyst and may incur Python serialization overhead ✓
  • C. It disables caching
  • D. It forces a broadcast

Explanation: Row-at-a-time Python UDFs are opaque to Catalyst (no pushdown/optimization) and serialize data between the JVM and Python. Prefer built-in functions or pandas/vectorized UDFs when possible.

18. Which function adds or replaces a column in a DataFrame?

  • A. select() only
  • B. withColumn() ✓
  • C. filter()
  • D. groupBy()

Explanation: withColumn('name', expr) returns a new DataFrame with the column added or replaced. It's a transformation and does not mutate the original (DataFrames are immutable).

19. spark.read with inferSchema=true on a large CSV is discouraged because it:

  • A. Is always wrong
  • B. Requires an extra pass over the data to infer types, costing time ✓
  • C. Cannot read CSV
  • D. Disables partitioning

Explanation: Schema inference makes Spark scan the data to deduce types, adding an extra job. Supplying an explicit schema (StructType) avoids that pass and prevents mis-inferred types.

20. A wide transformation creates a new ____ in the DAG.

  • A. job
  • B. stage ✓
  • C. partition
  • D. executor

Explanation: Wide transformations require a shuffle, which introduces a stage boundary — so a new stage is created. Jobs are triggered by actions; stages are split at shuffle boundaries; tasks run per partition.

21. Which storage level keeps cached data only in memory and recomputes partitions that don't fit?

  • A. DISK_ONLY
  • B. MEMORY_ONLY ✓
  • C. OFF_HEAP
  • D. MEMORY_AND_DISK_SER only

Explanation: MEMORY_ONLY stores deserialized objects in memory; partitions that don't fit are not stored and get recomputed when needed. MEMORY_AND_DISK spills the overflow to disk instead of recomputing.

22. What does repartition(col) (by column) do?

  • A. Sorts the data globally
  • B. Hash-partitions rows by the column via a shuffle so same-key rows share partitions ✓
  • C. Removes duplicates
  • D. Coalesces without shuffle

Explanation: repartition(col) performs a shuffle that hash-partitions rows on the column, co-locating equal keys — useful before key-based operations. It's a full shuffle, unlike coalesce.

23. Which is an action that writes results and triggers execution?

  • A. df.write.save(path) ✓
  • B. df.select()
  • C. df.withColumnRenamed()
  • D. df.filter()

Explanation: Writing (df.write.save/parquet/format...save) is an action that triggers the whole plan to execute and persist output. The others are lazy transformations.

24. To combine two DataFrames with identical schemas by stacking rows, use:

  • A. join()
  • B. unionByName() / union() ✓
  • C. crossJoin()
  • D. groupBy()

Explanation: union()/unionByName() stack rows of DataFrames with matching schemas. unionByName matches columns by name (safer); union matches by position. join combines columns, not rows.

25. The Catalyst optimizer is responsible for:

  • A. Managing cluster nodes
  • B. Optimizing the logical/physical query plan (pushdown, pruning, reordering) ✓
  • C. Storing data on disk
  • D. Scheduling jobs to executors

Explanation: Catalyst is Spark SQL's query optimizer — it rewrites and optimizes the plan (predicate pushdown, column pruning, join reordering) before code generation. The scheduler and cluster manager handle execution/resources.

26. Which method removes duplicate rows across all columns?

  • A. distinct() ✓
  • B. drop()
  • C. dropna()
  • D. limit()

Explanation: distinct() returns unique rows (a wide transformation requiring a shuffle). dropDuplicates(subset) deduplicates on chosen columns; dropna removes nulls.

27. df.filter(col('x') > 5) and df.where('x > 5') are:

  • A. Different operations
  • B. Equivalent (where is an alias of filter) ✓
  • C. Both actions
  • D. Invalid

Explanation: where() is an alias for filter(); both are lazy transformations that keep rows meeting the condition, accepting either a Column expression or a SQL string.

28. groupBy('k').agg(sum('v')) triggers a:

  • A. Narrow transformation
  • B. Wide transformation (shuffle) ✓
  • C. Action immediately
  • D. Broadcast

Explanation: Grouping by key requires rows with the same key to be co-located, causing a shuffle — a wide transformation and a new stage. It's still lazy until an action runs.

29. Which is TRUE about broadcast join thresholds?

  • A. Spark never auto-broadcasts
  • B. Tables under spark.sql.autoBroadcastJoinThreshold are auto-broadcast ✓
  • C. All joins are broadcast
  • D. Broadcast requires RDDs

Explanation: Spark auto-broadcasts a side estimated to be under autoBroadcastJoinThreshold (default 10MB). You can also force it with the broadcast() hint; AQE can broadcast at runtime too.

30. orderBy() on a full DataFrame is expensive because it:

  • A. Requires a global sort (shuffle across partitions) ✓
  • B. Is an action
  • C. Deletes data
  • D. Cannot be done

Explanation: A global orderBy needs a range/shuffle to produce a total ordering across partitions, which is costly. sortWithinPartitions avoids the global shuffle when only per-partition order is needed.

31. Which returns the number of partitions of a DataFrame?

  • A. df.rdd.getNumPartitions() ✓
  • B. df.count()
  • C. df.columns
  • D. df.schema

Explanation: df.rdd.getNumPartitions() reports the current partition count — useful when deciding whether to repartition/coalesce. count() returns row count; columns/schema return structure.

32. A Python (non-vectorized) UDF processes data:

  • A. In the JVM directly
  • B. Row-by-row with serialization between JVM and Python (slower) ✓
  • C. Only on the driver
  • D. Without any overhead

Explanation: Standard PySpark UDFs run row-at-a-time in a Python worker, requiring (de)serialization to/from the JVM — slower and opaque to Catalyst. Pandas UDFs batch data (Arrow) for better performance.

33. Which is an action that returns all rows to the driver (use with caution)?

  • A. collect() ✓
  • B. select()
  • C. filter()
  • D. repartition()

Explanation: collect() brings the entire result to the driver, risking OOM on large data. Prefer take()/show() for samples, or write() to persist full results.

34. coalesce(1) before writing produces:

  • A. Many output files
  • B. A single output file/partition, but can bottleneck by reducing parallelism ✓
  • C. Faster parallel writes
  • D. An error

Explanation: coalesce(1) merges to one partition so the write yields a single file, but it serializes the final stage onto one task — acceptable for small outputs, harmful for large ones.

35. The functions module (F.col, F.when, F.lit) is used to:

  • A. Manage clusters
  • B. Build column expressions in the DataFrame API ✓
  • C. Read files
  • D. Schedule jobs

Explanation: pyspark.sql.functions provides column expression builders (col, lit, when, aggregates, window fns) used to construct transformations that Catalyst can optimize.

36. A window spec Window.partitionBy('dept').orderBy('salary') with rank() computes:

  • A. A global total
  • B. A ranking of rows within each department by salary ✓
  • C. A join
  • D. A shuffle-free aggregate

Explanation: The window partitions by dept and orders by salary, so rank() assigns ranks within each department — a classic per-group ranking without collapsing rows.

37. Predicate pushdown means Spark:

  • A. Runs filters on the driver
  • B. Pushes filter conditions to the data source so less data is read ✓
  • C. Ignores filters
  • D. Broadcasts the filter

Explanation: Predicate pushdown sends filters down to the source/scan (e.g., Parquet/Delta), so irrelevant data is skipped at read time — a key Catalyst optimization reducing I/O.

38. Which describes a DataFrame's immutability?

  • A. You can modify it in place
  • B. Transformations return new DataFrames; the original is unchanged ✓
  • C. It cannot be cached
  • D. It has no schema

Explanation: DataFrames are immutable — each transformation yields a new DataFrame while the source stays intact, which underpins Spark's lineage-based fault tolerance and lazy optimization.

39. withColumnRenamed('old','new') does what?

  • A. Drops a column
  • B. Renames a column, returning a new DataFrame ✓
  • C. Casts a column
  • D. Filters rows

Explanation: withColumnRenamed returns a new DataFrame with the specified column renamed — a lazy transformation; the original DataFrame is unchanged.

40. Which function fills null values in specified columns?

  • A. na.fill(value) ✓
  • B. drop()
  • C. explode()
  • D. collect()

Explanation: df.na.fill(value [, subset]) replaces nulls with a value; df.na.drop() removes rows containing nulls. Both are transformations.

41. The number of tasks in a stage is determined by:

  • A. The number of executors
  • B. The number of partitions of its input ✓
  • C. The driver memory
  • D. The number of columns

Explanation: Each partition becomes one task in a stage, so the partition count sets task parallelism. Too few partitions underutilize the cluster; too many create scheduling overhead.

42. Which is TRUE about spark.read.parquet vs schema handling?

  • A. Parquet has no schema
  • B. Parquet stores its schema, so Spark reads it without inference (efficient) ✓
  • C. You must always supply a schema
  • D. It cannot be partitioned

Explanation: Parquet is self-describing (schema in the footer), so Spark reads types without a costly inference pass — one reason it's preferred over CSV for performance.

43. agg() after groupBy can compute multiple aggregations by:

  • A. Only one at a time
  • B. Passing several aggregate expressions (e.g., F.sum, F.avg) together ✓
  • C. Using collect()
  • D. Using explode()

Explanation: df.groupBy('k').agg(F.sum('v'), F.avg('v'), F.max('v')) computes several aggregates in one pass, each producing a column in the result.

44. A left outer join keeps:

  • A. Only matching rows
  • B. All left rows plus matched right columns (nulls where unmatched) ✓
  • C. All right rows only
  • D. The Cartesian product

Explanation: Left outer join preserves every left row, attaching right columns where the join key matches and nulls otherwise — used to retain the left dataset fully.

45. spark.sql('SELECT ...') returns:

  • A. A string
  • B. A DataFrame ✓
  • C. An RDD only
  • D. Nothing

Explanation: spark.sql runs SQL against registered tables/views and returns a DataFrame, interoperable with the DataFrame API — useful to mix SQL and Python.

46. Persisting with MEMORY_AND_DISK differs from MEMORY_ONLY by:

  • A. Never using memory
  • B. Spilling partitions that don't fit in memory to disk instead of recomputing ✓
  • C. Encrypting data
  • D. Disabling caching

Explanation: MEMORY_AND_DISK keeps what fits in memory and spills the rest to disk, avoiding recomputation. MEMORY_ONLY recomputes overflow partitions when needed.

47. Which action writes a DataFrame as a managed table?

  • A. df.write.saveAsTable('name') ✓
  • B. df.select()
  • C. df.cache()
  • D. df.printSchema()

Explanation: saveAsTable persists the DataFrame as a table in the metastore (an action). save()/parquet() write to a path; select/cache/printSchema don't write data.

48. Broadcasting a large table is a bad idea because it:

  • A. Is always faster
  • B. Copies the whole table to every executor, risking memory pressure/OOM ✓
  • C. Disables joins
  • D. Requires RDDs

Explanation: Broadcast replicates a table to all executors; doing this with a large table wastes memory and can cause OOM. Broadcast only small tables (under the threshold).

49. Which reads only needed columns from Parquet, reducing I/O?

  • A. Column pruning (projection pushdown) ✓
  • B. collect()
  • C. explode()
  • D. coalesce()

Explanation: Column pruning (projection pushdown) reads only the columns a query references from columnar formats like Parquet/Delta, cutting I/O — an automatic Catalyst optimization.

50. The difference between cache() and persist() is:

  • A. cache() lets you choose a storage level; persist() does not
  • B. cache() is persist() with the default storage level (MEMORY_AND_DISK for DataFrames) ✓
  • C. They are unrelated
  • D. persist() is an action

Explanation: cache() is shorthand for persist() using the default storage level; persist(level) lets you specify a level (e.g., MEMORY_ONLY, DISK_ONLY). Both are lazy hints.

51. select(F.expr('a + b AS c')) demonstrates:

  • A. A SQL string expression inside the DataFrame API ✓
  • B. An action
  • C. A shuffle
  • D. A broadcast

Explanation: F.expr parses a SQL expression string into a Column, letting you use SQL syntax within DataFrame transformations (also selectExpr does this).

52. Which returns distinct counts per group efficiently in the DataFrame API?

  • A. groupBy('k').agg(countDistinct('v')) ✓
  • B. collect()
  • C. explode('v')
  • D. coalesce(1)

Explanation: groupBy(...).agg(countDistinct('v')) computes unique counts per group. It involves a shuffle (wide) but is the idiomatic, optimizable approach versus collecting to the driver.

53. pivot() in Spark is used to:

  • A. Rotate rows into columns based on distinct values of a column (after groupBy) ✓
  • B. Delete columns
  • C. Cache data
  • D. Broadcast a table

Explanation: df.groupBy('a').pivot('b').agg(...) turns distinct values of b into columns — a wide aggregation useful for cross-tab summaries.

54. Which is TRUE about the DAG scheduler?

  • A. It executes tasks itself
  • B. It splits jobs into stages at shuffle boundaries and submits task sets ✓
  • C. It stores data
  • D. It manages the cluster nodes

Explanation: The DAGScheduler divides a job into stages (cut at shuffle dependencies) and hands task sets to the TaskScheduler, which places tasks on executors.

55. spark.conf.set('spark.sql.shuffle.partitions', 400) changes:

  • A. Executor count
  • B. The number of partitions produced by shuffles for SQL/DataFrame ops ✓
  • C. The driver memory
  • D. The storage format

Explanation: It sets how many partitions shuffles create (default 200). Tuning it balances parallelism and overhead; AQE can also coalesce these at runtime.

56. Which action counts rows without bringing data to the driver?

  • A. count() ✓
  • B. collect()
  • C. toPandas()
  • D. take(1000000)

Explanation: count() returns just the row count (an aggregate) — safe on large data. collect()/toPandas() pull all rows to the driver and can OOM.

57. A window function requires:

  • A. No specification
  • B. A Window spec (partitionBy/orderBy) defining the frame ✓
  • C. A broadcast
  • D. A cache

Explanation: Window functions operate over a Window specification (partitioning and ordering, optionally a frame), computing values across related rows without collapsing them.

58. Which is a narrow transformation?

  • A. join
  • B. groupBy
  • C. map/filter/select ✓
  • D. distinct

Explanation: map, filter, select, and withColumn are narrow — each output partition depends on a single input partition, so no shuffle. join/groupBy/distinct are wide.

59. toPandas() should be used only when:

  • A. The dataset is large
  • B. The result is small enough to fit in the driver's memory ✓
  • C. You want distributed processing
  • D. Never

Explanation: toPandas() collects the DataFrame to a single Pandas DataFrame on the driver — fine for small results, dangerous for large ones (OOM). Keep heavy work in Spark.

60. Which describes lazy evaluation's benefit for joins?

  • A. It runs joins immediately
  • B. Catalyst can reorder/choose join strategies and push filters before execution ✓
  • C. It disables optimization
  • D. It forces broadcast

Explanation: Because execution is deferred, Catalyst sees the whole plan and can pick the best join strategy, push down predicates, and prune columns before anything runs.

61. dropDuplicates(['id']) differs from distinct() by:

  • A. Being identical
  • B. Deduplicating based only on the specified subset of columns ✓
  • C. Only working on RDDs
  • D. Never shuffling

Explanation: dropDuplicates(subset) removes rows duplicated on the given columns (keeping one), whereas distinct() considers all columns. Both are wide transformations.

62. Which reads a Delta table by path in the DataFrame API?

  • B. spark.read.text('/path')
  • C. spark.read.json('/path') only
  • D. spark.sql('/path')

Explanation: spark.read.format('delta').load(path) (or spark.read.table('name')) reads a Delta table into a DataFrame. text/json readers are for those raw formats.

63. Salting a skewed join key helps by:

  • A. Encrypting the key
  • B. Spreading hot keys across multiple partitions to balance the shuffle ✓
  • C. Removing the join
  • D. Broadcasting the large side

Explanation: Adding a random 'salt' to a heavily-skewed key distributes its rows across partitions, relieving the straggler task — a manual complement to AQE skew handling.

64. Which is TRUE about RDDs vs DataFrames for the exam's focus?

  • B. DataFrames use Catalyst/Tungsten optimizations; RDDs are lower-level and unoptimized ✓
  • C. They are identical
  • D. DataFrames can't be cached

Explanation: DataFrames benefit from the Catalyst optimizer and Tungsten execution, generally outperforming hand-written RDD code, which is lower-level and not query-optimized.

66. Which is TRUE about the difference between select and selectExpr?

  • D. selectExpr is an action

Explanation: selectExpr parses SQL strings (e.g., 'a+b AS c'), while select works with column names/Column expressions. Both are transformations returning a new DataFrame.

67. cache() then an action, then reuse: the second action:

  • A. Recomputes from source
  • B. Reads from cache, avoiding recomputation of the lineage ✓
  • C. Fails
  • D. Ignores the cache

Explanation: Once materialized by the first action, cached data is reused by subsequent actions, skipping recomputation of the upstream lineage.

68. Which is a wide transformation that changes partition count with a full shuffle?

  • A. coalesce
  • B. repartition ✓
  • C. filter
  • D. select

Explanation: repartition performs a full shuffle and can increase or decrease partitions. coalesce avoids a full shuffle and only decreases; filter/select are narrow.

  • B. Reducing rows before the join lowers shuffle volume and speeds the join ✓
  • C. It has no effect
  • D. It forces a cross join

Explanation: Filtering early (or letting Catalyst push predicates down) shrinks the data joined, reducing shuffle and improving performance.

71. The lit() function is used to:
