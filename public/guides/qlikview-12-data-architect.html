QlikView 12 Data Architect (QV12DA) — Study Guide

Data architecture in QlikView: load scripting, data modeling and key handling, QVDs and incremental load, resolving synthetic keys/circular references, Section Access, and performance optimization.

~50 questions · 120 minutes · scenario-based on QlikView scripting and modeling · passing per Qlik scoring.

What it is

The QlikView 12 Data Architect (QV12DA) validates data-architecture skills in QlikView: load scripting, data modeling and key handling, QVDs and incremental loading, resolving synthetic keys and circular references, Section Access, and performance optimization on the same associative engine as Qlik Sense.

It proves you can engineer reliable, performant QlikView data models and reload architectures — the technical backbone of enterprise QlikView deployments.

Where it's used

  • Roles: QlikView Developer/Data Architect, BI Developer maintaining QlikView estates.
  • On the job: building QVD staging layers, incremental loads, clean associative models, and secure, optimized QlikView documents.
  • Career value: validates deep QlikView engineering skills, valuable for organizations with established QlikView platforms.
  • For this portfolio: reflects early enterprise BI work, including connector-less SAP-to-BI integration and heavy report re-engineering.

In plain English

  • Same associative engine as Qlik Sense: tables snap together on matching column names. Build the model by naming keys carefully.
  • A three-layer QVD setup is a supply chain: Extract raw to QVD → Transform/model → Present curated QVD to the app. Each stage is reusable and fast.
  • Incremental load = only fetch what changed and add it to the stored QVD, instead of reloading everything each night.
  • Section Access is the bouncer: it checks who you are and only lets you see your allowed rows.

Exam shortcut tricks

  1. Synthetic key = 2+ shared fields; circular reference = association loop. Resolve with renames, composite keys, or a link table.
  2. KEEP = reduce two tables to matching rows but keep them SEPARATE. JOIN = merge into ONE table. Know the difference.
  3. Optimized QVD load breaks with transformations/WHERE — except one WHERE EXISTS(field). Renaming/adding fields also breaks it.
  4. BINARY load copies another QVW's whole model and MUST be the first statement, used once.
  5. Incremental with updates: load changed rows from source, then keep old QVD rows WHERE NOT EXISTS(key); handle deletes by reconciling current keys.
  6. AutoNumber() for compact keys; split datetime into Date+Time to cut cardinality/memory.
  7. Section Access: UPPERCASE fields/values, keep a valid ADMIN, test in a copy (a bad setup locks everyone out).

Study roadmap

Study notes

Model quality

  • Same associative engine as Qlik Sense: tables link on identically named fields.
  • Synthetic keys arise when tables share 2+ fields; resolve by renaming/combining keys.
  • Circular references form association loops; break them with renaming or a link table.

QVD & incremental

  • QVDs stage data for speed and reuse; optimized loads (no transforms/most WHEREs) are fastest.
  • Incremental load: pull only changed rows from source, then concatenate with existing QVD, handling inserts/updates/deletes.

Section Access

  • Defined in script with fields like ACCESS, USERID/NTNAME, and reduction fields (typically uppercase).
  • ADMIN vs USER access levels; strict/initial reduction controls what data each user sees.

Combining tables

  • CONCATENATE = union of rows; JOIN = merge columns (can duplicate rows); KEEP = like a join but keeps tables separate, reducing to the intersection/one side.
  • ApplyMap adds a single looked-up value without row duplication.

Practice questions (100)

1. In QlikView, tables are associated based on:

  • A. Primary keys defined in a UI
  • B. Fields with identical names ✓
  • C. Load order
  • D. Bookmark settings

Explanation: QlikView uses the same associative engine as Qlik Sense — tables associate automatically on fields sharing the same name. Field naming drives the model.

2. Which situation produces a synthetic key?

  • A. Tables share exactly one field
  • B. Tables share two or more fields ✓
  • C. A QVD is loaded
  • D. ApplyMap is used

Explanation: When two or more tables share two or more field names, QlikView builds a synthetic key table to manage the composite association. It's usually undesirable and resolved by renaming or explicitly combining keys.

3. What distinguishes KEEP from JOIN in QlikView?

  • A. KEEP merges tables into one; JOIN keeps them separate
  • B. KEEP keeps the tables separate but reduces them like a join; JOIN merges into a single table ✓
  • C. They are identical
  • D. KEEP only works on QVDs

Explanation: JOIN physically merges two tables into one. KEEP performs the same record-matching reduction (inner/left/right) but leaves the two tables as separate tables in the model — useful to reduce data without merging columns.

4. An optimized QVD load is broken when you:

  • A. Load the QVD as-is
  • B. Add transformations or a WHERE clause on a non-indexed field ✓
  • C. Rename the QVD file
  • D. Store it to disk

Explanation: Optimized loads read the QVD nearly directly into memory. Applying transformations, new fields, or WHERE conditions (except a single WHERE EXISTS on one field) forces an unoptimized, slower load.

5. In Section Access, reduction fields are conventionally written in:

  • A. lowercase
  • B. UPPERCASE ✓
  • C. camelCase
  • D. any case — it doesn't matter

Explanation: Section Access matching is case-sensitive and conventionally uses UPPERCASE for fields and values (e.g., USERID, NTNAME, and the reduction field) to ensure reliable matching against authenticated users.

6. A circular reference is best resolved by:

  • A. Adding another shared field
  • B. Renaming fields to break the loop or introducing a link table ✓
  • C. Deleting Section Access
  • D. Switching to an unoptimized load

Explanation: Circular references (association loops) create ambiguity. Break the loop by renaming/qualifying fields or restructuring with a link table so the model resolves associations unambiguously.

7. The primary purpose of staging data in QVD files is:

  • A. To encrypt data
  • B. Fast reuse/reload and enabling incremental loads ✓
  • C. To create charts
  • D. To define Section Access

Explanation: QVDs store data in Qlik's optimized binary format for very fast reloads and reuse across apps, and they underpin incremental-load architectures that avoid reloading all source data each time.

8. To add a single lookup value to a large fact table without duplicating rows, use:

  • A. Outer JOIN
  • B. ApplyMap with a mapping table ✓
  • C. CONCATENATE
  • D. A synthetic key

Explanation: ApplyMap performs a key-based lookup that returns one value per row and never multiplies rows, making it faster and safer than a JOIN for enriching a fact table with a single field.

9. In an incremental load, records that were updated at source are typically handled by:

  • A. Ignoring them
  • B. Loading changed rows and removing superseded rows (e.g., WHERE NOT EXISTS on the key) before concatenating ✓
  • C. Reloading the whole source
  • D. Using a gauge chart

Explanation: For updates, you load the new/changed rows and exclude the old versions from the stored QVD (commonly a WHERE NOT EXISTS on the primary key) so the concatenated result reflects current values without duplicates.

10. Which practice improves QlikView data-model performance?

  • A. Maximizing distinct values in key fields
  • B. Removing synthetic keys and keeping key fields low-cardinality where possible ✓
  • C. Adding circular references
  • D. Avoiding QVDs

Explanation: Clean keys matter: eliminating synthetic keys, reducing unnecessary distinct key values, and using optimized QVD loads all reduce memory use and speed up reloads and calculations.

11. In QlikView, the Binary load statement is used to:

  • A. Load a CSV
  • B. Load the entire data model from another QVW file ✓
  • C. Create a QVD
  • D. Apply Section Access

Explanation: BINARY loads the complete data model from another QlikView document (.qvw). It must be the very first statement in the script and can appear only once.

12. The ApplyMap function is preferred over JOIN for single-value lookups because it:

  • A. Encrypts the value
  • B. Does not risk duplicating rows and is typically faster ✓
  • C. Creates a synthetic key
  • D. Requires three columns

Explanation: ApplyMap performs a row-wise lookup returning one value and never multiplies rows, unlike JOIN which can duplicate rows if the key isn't unique — making it safer and faster for enrichment.

13. A WHERE NOT EXISTS(PrimaryKey) clause in an incremental load:

  • A. Loads all rows
  • B. Appends only rows whose key is not already in memory, avoiding duplicates ✓
  • C. Deletes the table
  • D. Applies Section Access

Explanation: It checks the key against already-loaded values and loads only new keys — the standard way to append fresh records during an incremental load without creating duplicates.

14. Which is TRUE about an optimized QVD load in QlikView?

  • A. You can add many transformations and keep it optimized
  • B. It stays optimized only with minimal manipulation (no new fields, at most a simple WHERE EXISTS on one field) ✓
  • C. It requires Section Access
  • D. It is always slower than unoptimized

Explanation: An optimized load reads the QVD almost directly into memory. Adding calculated fields, transformations, or complex WHERE clauses breaks optimization, forcing a slower unoptimized load.

15. Section Access in QlikView typically stores user identities using which field?

  • A. USERID or NTNAME ✓
  • B. SALES
  • C. DATE
  • D. PRODUCT

Explanation: Section Access tables use fields like ACCESS, USERID/PASSWORD or NTNAME (Windows identity), plus reduction fields — conventionally uppercase — to map users to permitted data.

16. The QUALIFY statement helps a data architect by:

  • A. Compressing QVDs
  • B. Prefixing field names to prevent unintended automatic associations ✓
  • C. Creating charts
  • D. Loading binaries

Explanation: QUALIFY renames fields as Table.Field so identically named fields across tables don't auto-associate — helpful for eliminating synthetic keys while structuring the model.

17. A synthetic key table appears in the QlikView data model viewer when:

  • A. Two tables share exactly one field
  • B. Two or more tables share two or more fields ✓
  • C. A QVD is loaded
  • D. Section Access is applied

Explanation: QlikView creates a synthetic key ($Syn) when tables share two or more fields, to manage the composite association. It's usually resolved by renaming or building an explicit key.

18. The MAPPING prefix creates a table that:

  • A. Is used only by ApplyMap/Map...Using and dropped after script ends ✓
  • B. Persists as a normal data table
  • C. Encrypts fields
  • D. Creates a QVD

Explanation: A MAPPING LOAD builds a special two-column mapping table used by ApplyMap or Map...Using; it is not part of the data model and is discarded when the script finishes.

19. IntervalMatch in QlikView is used to:

  • A. Match discrete values (e.g., a date) to ranges defined by From/To fields ✓
  • B. Concatenate tables
  • C. Create Section Access
  • D. Compress data

Explanation: IntervalMatch links discrete values to numeric/date intervals (From–To), commonly used for slowly changing dimensions or bucketing values into bands.

20. To reduce memory from a high-cardinality composite key, an architect can use:

  • A. AutoNumber() / AutoNumberHash ✓
  • B. Section Access
  • C. A gauge chart
  • D. A bookmark

Explanation: AutoNumber()/AutoNumberHash128() convert composite/text keys into compact integer keys, lowering memory use and speeding associations for large tables.

21. Which load reads from a table already in memory for further processing?

  • A. RESIDENT load ✓
  • B. BINARY load
  • C. SELECT from DB
  • D. MAPPING load

Explanation: LOAD ... RESIDENT reads an in-memory table loaded earlier in the script, enabling further transformation/aggregation without re-querying the source.

22. A circular reference is flagged by QlikView because it:

  • A. Improves performance
  • B. Creates ambiguous association paths between tables ✓
  • C. Encrypts data
  • D. Is required for QVDs

Explanation: A loop of associations gives multiple paths between tables, making results ambiguous. QlikView loosens one table automatically, but architects should resolve it via renaming or a link table.

23. Storing intermediate results as QVDs in a multi-layer (staging) architecture mainly improves:

  • A. Chart colors
  • B. Reload performance and reusability across apps ✓
  • C. Section Access
  • D. Synthetic keys

Explanation: A QVD staging layer lets multiple apps reuse pre-processed data and enables fast, optimized reloads and incremental patterns — a core data-architecture best practice.

24. The QlikView Table Viewer (Ctrl+T) is primarily used to:

  • A. Build charts
  • B. Inspect the data model, associations, and detect synthetic keys ✓
  • C. Apply Section Access
  • D. Schedule reloads

Explanation: The Table Viewer shows tables, fields, and their associations, making it the go-to tool to spot synthetic keys, circular references, and unintended links.

25. Loosely coupled tables in QlikView (from a circular reference) mean:

  • A. Faster associations
  • B. One table's association is severed to break the loop, which can give unexpected results ✓
  • C. Encrypted data
  • D. Better performance guaranteed

Explanation: QlikView automatically 'loosens' a table to break a circular reference, but this can produce non-intuitive results — so architects should resolve loops explicitly (rename/link table).

26. The Concatenate prefix is required when two tables:

  • A. Have identical fields (auto-concatenation already applies)
  • B. Have different field sets but should be appended into one table ✓
  • C. Are QVDs
  • D. Need Section Access

Explanation: Auto-concatenation happens only when field sets match exactly. Use the explicit CONCATENATE prefix to force appending tables with differing fields (missing values become null).

27. In an incremental load with inserts and updates, the typical sequence is:

  • A. Load all from source only
  • B. Load new/updated rows from source, then concatenate older QVD rows WHERE NOT EXISTS(key) ✓
  • C. Delete the QVD
  • D. Apply Section Access

Explanation: You fetch changed rows from source, then append the still-valid stored rows using WHERE NOT EXISTS on the key (so updated keys are taken from the fresh source data), and STORE back to QVD.

28. Which function returns the maximum value of a field already loaded, for incremental cutoffs?

  • A. Peek()/FieldValue with Max, or a preceding Max() load ✓
  • B. Subfield()
  • C. ApplyMap()
  • D. Only()

Explanation: Architects capture the last loaded max (e.g., via a resident Max() load or Peek on a sorted field) to build the WHERE clause that pulls only newer source rows.

29. The MAPPING ... USING statement applies a mapping to:

  • A. A single field automatically during load (renaming values) ✓
  • B. Create a chart
  • C. Section Access
  • D. A QVD file

Explanation: MAP Field USING MapTable applies a mapping table to automatically translate values of a field during subsequent loads — an alternative to calling ApplyMap explicitly.

30. Which is TRUE about QVD layers in a three-tier architecture (Extract/Transform/Load)?

  • A. They add no value
  • B. Extractors pull raw to QVD, transformers model it, and the app loads curated QVDs — improving reuse and reload speed ✓
  • C. They require Section Access
  • D. They break associations

Explanation: A layered QVD architecture (extract → transform → present) separates concerns, promotes reuse, speeds reloads via optimized QVD reads, and simplifies maintenance.

31. To prevent a descriptive field (e.g., 'Description') in two tables from associating them, you can:

  • A. Rename one of them or QUALIFY ✓
  • B. Add a synthetic key
  • C. Use a gauge
  • D. Apply Section Access

Explanation: Renaming (AS) or using QUALIFY prevents the coincidentally-shared field from creating an unwanted association or synthetic key.

32. Section Access reduction typically requires the reduction field to be:

  • A. Present in both the Section Access and Section Application data, uppercase ✓
  • B. Only in charts
  • C. A QVD
  • D. Lowercase only

Explanation: The reduction field must exist in both the access table and the application data (matching, typically uppercase) so QlikView can reduce each user's data to permitted values.

33. The Buffer prefix on a load:

  • A. Encrypts data
  • B. Automatically caches the load as a QVD and reuses it (e.g., incremental/stale options) ✓
  • C. Creates Section Access
  • D. Splits fields

Explanation: BUFFER auto-creates and reuses a QVD buffer for a load, optionally with incremental or stale-after settings — a shortcut for QVD caching without manual STORE/LOAD.

34. A best practice to reduce reload time on large source tables is to:

  • A. Always full reload
  • B. Use incremental loads with QVD staging and optimized reads ✓
  • C. Avoid QVDs
  • D. Add synthetic keys

Explanation: Incremental loading plus a QVD staging layer (optimized reads) minimizes source extraction and processing time for large, frequently updated data.

35. The Keep prefix (Left/Right/Inner) differs from Join by:

  • A. Merging tables into one
  • B. Reducing the tables to matching records while keeping them as separate tables ✓
  • C. Encrypting fields
  • D. Creating QVDs

Explanation: KEEP performs the same matching as a Join but leaves the two tables separate (only reducing their rows), whereas JOIN merges columns into a single table.

36. Which practice best avoids memory bloat from timestamp fields?

  • A. Keep full datetime with seconds everywhere
  • B. Split date and time into separate fields / reduce precision ✓
  • C. Store as text
  • D. Add a synthetic key

Explanation: High-precision datetime fields have huge cardinality. Splitting into date and time (and reducing precision) drastically lowers distinct values and memory use.

37. The QVD Header contains metadata such as:

  • A. Only raw bytes
  • B. Field names, record count, and lineage info enabling optimized loads ✓
  • C. Chart definitions
  • D. Section Access rules

Explanation: A QVD's XML header stores metadata (fields, record count, creation info) that lets QlikView perform fast optimized loads and inspect contents.

38. Which statement forces fields to associate by creating an explicit composite key?

  • A. AutoNumber(Field1 & '|' & Field2) AS %Key ✓
  • B. DISTINCT
  • C. Section Access
  • D. Gauge()

Explanation: Concatenating fields into one key (often wrapped in AutoNumber to save memory) creates a single explicit key, avoiding synthetic keys from multiple shared fields.

39. A partial reload in QlikView:

  • A. Reloads everything
  • B. Runs only Add/Replace/Delete-tagged load statements to update part of the model ✓
  • C. Deletes the document
  • D. Creates Section Access

Explanation: Partial reload executes only statements marked with prefixes like Add, Replace, or Delete, updating portions of the model without a full reload — faster for incremental UI refreshes.

40. Which is TRUE about storing a resident table to QVD?

  • A. You cannot store resident tables
  • B. STORE ResidentTable INTO file.qvd (qvd) writes it for reuse ✓
  • C. It requires Section Access
  • D. It deletes the table

Explanation: You can STORE any in-memory (including resident/derived) table to a QVD, enabling staging of transformed data for reuse and incremental loads.

41. To avoid loading sensitive columns for unauthorized users, combine Section Access with:

  • A. Column-level omission/reduction and reduction fields ✓
  • B. A gauge
  • C. ApplyMap only
  • D. Crosstable

Explanation: Section Access can reduce rows by user and, with techniques like omitting fields (OMIT) or conditional loads, limit column exposure — layered data security.

42. The Inner Keep between two tables results in:

  • A. One merged table
  • B. Both tables reduced to only the records whose keys match, kept separate ✓
  • C. A Cartesian product
  • D. A QVD

Explanation: Inner Keep reduces both tables to their matching key intersection while keeping them as separate tables — unlike Inner Join which merges them.

43. Which improves an unavoidable large JOIN's performance?

  • A. Joining on high-cardinality text keys
  • B. Reducing columns/rows first and joining on compact (AutoNumber) keys ✓
  • C. Adding synthetic keys
  • D. Disabling QVDs

Explanation: Trimming unnecessary columns/rows before the join and using compact integer keys reduces memory and speeds the join versus joining wide tables on large text keys.

44. A generic load's output typically needs to be:

  • A. Left as many tables
  • B. Recombined (e.g., via joins/keep) since it produces one table per attribute ✓
  • C. Encrypted
  • D. Stored as CSV only

Explanation: GENERIC LOAD creates a separate table per attribute; these usually must be linked back together (joins/keep on the key) to form a usable wide table.

45. The main reason to use variables for file paths in scripts is:

  • A. Decoration
  • B. Maintainability and easy environment switching (dev/prod) ✓
  • C. To create synthetic keys
  • D. To apply Section Access

Explanation: Centralizing paths/connection info in variables makes scripts easier to maintain and to point at different environments without editing every statement.

46. Which is TRUE about incremental load 'Insert only' scenarios?

  • A. They must handle updates and deletes
  • B. They are the simplest — just append new keys via WHERE NOT EXISTS ✓
  • C. They require a link table
  • D. They cannot use QVDs

Explanation: Insert-only sources (no updates/deletes) are simplest: load new rows (WHERE NOT EXISTS on the key) and concatenate with the stored QVD.

47. The Table Viewer's 'Preview' pane helps verify:

  • A. Chart colors
  • B. Actual field values and that transformations produced expected data ✓
  • C. Section Access only
  • D. Cluster size

Explanation: Previewing sample rows in the Table Viewer confirms fields loaded and transformed correctly — a quick sanity check during model development.

48. Which reduces the risk of a bad incremental load corrupting the QVD?

  • A. Overwrite in place with no checks
  • B. Load/validate to a temp table, then store; keep a backup/version of the QVD ✓
  • C. Disable EXISTS checks
  • D. Add synthetic keys

Explanation: Validating before storing and retaining a prior QVD version guards against corrupting the authoritative dataset if a load has issues — a robustness best practice.

49. Mapping load performance vs ApplyMap at query time: ApplyMap resolves:

  • A. At chart render time
  • B. During the load (values are materialized into the field) ✓
  • C. In Section Access
  • D. Never

Explanation: ApplyMap resolves lookups during the load and stores the resulting value in the field, so there's no per-query lookup cost — efficient for static enrichment.

50. Which is TRUE about the order of load statements and associations?

  • A. Order never matters
  • B. The order affects which table 'owns' a field name and can influence concatenation/associations ✓
  • C. Only the first statement runs
  • D. Associations are random

Explanation: Load order matters: auto-concatenation and field ownership depend on what's already loaded, so architects sequence loads deliberately.

51. A stored procedure result from SQL SELECT is loaded by:

  • A. BINARY
  • B. SQL SELECT (or SQL EXEC) after connecting, then LOAD to bring it into the model ✓
  • C. MAPPING
  • D. CROSSTABLE

Explanation: After a connection, SQL SELECT/EXEC retrieves rows from the database (including procedures where supported), which a preceding LOAD then materializes in QlikView.

52. To avoid reloading unchanged historical data daily, implement:

  • A. Full reload
  • B. Incremental load with a QVD holding history and only new rows from source ✓
  • C. Synthetic keys
  • D. Section Access

Explanation: Incremental loading keeps history in a QVD and only pulls new/changed rows from the source, drastically reducing reload time and source impact.

53. Which is the safest handling of updates in incremental load?

  • A. Append new rows only (creates duplicates on update)
  • B. Load changed rows from source, then keep old QVD rows WHERE NOT EXISTS(key) ✓
  • C. Delete the QVD
  • D. Ignore updates

Explanation: Taking updated rows from source and retaining old rows only where the key doesn't already exist ensures updated records use fresh values without duplication.

54. Which reduces the chance of a circular reference in a multi-fact model?

  • A. Sharing many field names across facts
  • B. A link table (or concatenated fact) connecting to shared dimensions ✓
  • C. Adding synthetic keys
  • D. Disabling QVDs

Explanation: A link table (or a concatenated fact with a source flag) provides a single, unambiguous path to shared dimensions, preventing circular references.

55. The purpose of a transformation (T) layer in the ETL/QVD architecture is to:

  • A. Store raw only
  • B. Clean, conform, and model data from extract QVDs before the app consumes it ✓
  • C. Render charts
  • D. Apply Section Access only

Explanation: The transform layer applies business rules, cleansing, key handling, and modeling on extracted QVDs, producing curated QVDs the presentation app loads.

56. Which function helps generate a date range/master calendar in script?

  • A. Repeat()
  • B. A combination of MinDate/MaxDate with a temp table and Date() (AutoGenerate/While) ✓
  • C. ApplyMap()
  • D. Peek() only

Explanation: Master calendars are generated by computing min/max dates and looping (AutoGenerate/While with iterno()) to create one row per date with derived fields.

57. Which memory issue arises from storing pre-joined wide tables?

  • A. Lower memory
  • B. Redundant repeated values increasing memory vs a normalized/star model ✓
  • C. No effect
  • D. Encryption

Explanation: Wide, denormalized tables repeat dimension values across many rows, using more memory than a star schema where dimensions are stored once and associated.

58. Which is TRUE about applying Section Access in QlikView?

  • A. It is only cosmetic
  • B. It reduces data per user based on matching the authenticated identity to reduction values ✓
  • C. It speeds all loads
  • D. It removes synthetic keys

Explanation: Section Access enforces row-level security by matching the user (USERID/NTNAME) to permitted reduction-field values, hiding non-permitted data.

59. Buffer (Incremental) prefix is a shortcut that:

  • A. Encrypts data
  • B. Automatically maintains an incremental QVD buffer for a load ✓
  • C. Creates charts
