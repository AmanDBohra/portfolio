Databricks Certified Data Engineer Professional — Study Guide

Advanced data engineering on Databricks: complex transformations and streaming, Delta optimization and modeling (CDC/SCD, medallion), security and governance, monitoring and logging, plus testing and CI/CD deployment.

~60 multiple-choice questions · 120 minutes · passing ~70% · Python & SQL, deeper scenarios than the Associate.

What it is

The Databricks Certified Data Engineer Professional is the advanced engineering credential. It goes beyond building pipelines to designing them well: complex Structured Streaming, Delta optimization (OPTIMIZE/ZORDER, liquid clustering, deletion vectors), dimensional modeling (CDC with Change Data Feed, SCD Type 1/2), security and governance, monitoring, and testing/CI-CD deployment with Databricks Asset Bundles.

Where the Associate proves you can make a pipeline work, the Professional proves you can make it correct, performant, secure, and maintainable at scale — the difference between a working job and a production-grade platform.

Where it's used

  • Roles: Senior/Lead Data Engineer, Data Platform Engineer, Streaming/Real-time Engineer, Data Architect.
  • On the job: tuning large Delta tables, designing exactly-once streaming and CDC/SCD pipelines, enforcing row/column security, and shipping via tested CI/CD.
  • Career value: a strong signal of senior engineering capability; often a differentiator for lead and architecture roles on Databricks.
  • For this portfolio: reflects the delivery-lead responsibility for performant, governed, production analytics on a large international engagement.

In plain English

  • If the Associate is learning to drive, the Professional is defensive driving in traffic: same car, but now you handle streaming rush-hour, breakdowns (retries), and passengers' safety (governance).
  • Change Data Feed is a security camera that records exactly what changed — which rows were added, edited, or removed — so downstream systems copy only the changes instead of redoing everything.
  • SCD Type 2 is keeping every version of your address on file with move-in/move-out dates, so you can answer 'where did they live in 2021?'. Type 1 just overwrites — no history.
  • A watermark is a 'we stop waiting for latecomers after X minutes' rule, so the system doesn't hold the door open forever (unbounded state).

Exam shortcut tricks

  1. 'Propagate only changes downstream' → Change Data Feed (CDF). 'Keep full history of a dimension' → SCD Type 2. These two keywords map directly to answers.
  2. Streaming reliability trio: checkpoint (resume/exactly-once), watermark (bound state for late data), trigger (how often). Know what each fixes.
  3. Trigger.AvailableNow = process everything available then stop (scheduled batch on a streaming source). Continuous = always on, low latency.
  4. Deletion vectors / merge-on-read = fast updates without rewriting whole files; OPTIMIZE later materializes them. Great for 'why is UPDATE slow / how to speed it up.'
  5. Idempotency = safe reruns. Achieve with MERGE on a key or txnAppId/txnVersion in foreachBatch.
  6. Security: dynamic views / Unity Catalog row filters + column masks for row/column security; VACUUM to physically erase deleted data (GDPR).
  7. Deploy the grown-up way: Git + CI tests + Databricks Asset Bundles (per-environment variables). 'Promote dev→prod as code' = Asset Bundles.

Study notes

Change Data Feed (CDF)

  • Enable with delta.enableChangeDataFeed = true (table property).
  • Read row-level changes (insert/update_preimage/update_postimage/delete) with readChangeFeed and startingVersion/startingTimestamp.
  • Ideal for propagating incremental changes downstream (silver→gold) without full recomputation.

Slowly Changing Dimensions

  • SCD Type 1 overwrites the old value (no history).
  • SCD Type 2 adds a new row per change with validity columns (e.g., start/end timestamps, is_current flag) — preserves full history.
  • MERGE INTO implements both; Type 2 closes the prior row and inserts a new current row.

Structured Streaming

  • Checkpointing (checkpointLocation) stores offsets + state for exactly-once processing and recovery.
  • Watermarks (withWatermark) bound state for late data in aggregations/joins so state doesn't grow unbounded.
  • Triggers: default (micro-batch ASAP), fixed interval (processingTime), availableNow (process all available then stop), continuous (low-latency).

Security patterns

  • Dynamic views apply row filters/column masks using current_user() / is_account_group_member() for fine-grained access.
  • Unity Catalog supports row-level security and column masking functions natively.

Hands-on projects

1. Real-time claims streaming with watermarks & exactly-once

Goal: Process a claims event stream into Delta with late-data handling and no duplicates on restart.

Architecture & data model: Claims event source (Kafka/files) → Structured Streaming with watermark → windowed aggregates → Delta sink via foreachBatch (idempotent), checkpointed for recovery.

Concepts covered:

  • Structured Streaming: Processes an unbounded claims event stream as incremental micro-batches into Delta.
  • Watermarking: withWatermark bounds how long late events are accepted so windowed state doesn't grow forever.
  • Stateful aggregations: Windowed counts/sums keep state across batches; the watermark expires old state.
  • Checkpointing: Persists offsets and state so the query resumes exactly-once after a restart.
  • Exactly-once / idempotency: txnAppId/txnVersion in foreachBatch (or MERGE on a key) prevents duplicate writes on retry.

Implementation steps:

  1. readStream the claims source; apply withWatermark on the event-time column.
  2. Aggregate windowed metrics (claims/hour by region) in update output mode.
  3. Write via foreachBatch with txnAppId/txnVersion for exactly-once.
  4. Set a checkpointLocation; tune trigger and maxOffsets/FilesPerTrigger.
  5. Test recovery by killing and restarting the stream.

Outcomes:

  • Near-real-time operational metrics with correct late-data handling.
  • Exactly-once results that survive restarts.
  • Bounded, predictable state and cost.

Stack: Structured Streaming, Delta Lake, foreachBatch

Advanced streaming reliability for time-sensitive insurance operations reporting.

2. SCD Type 2 + Change Data Feed propagation

Goal: Maintain full history of policy/distributor dimensions and propagate only changes downstream.

Architecture & data model: Silver dimension maintained as SCD2 via MERGE; CDF enabled. Gold consumes readChangeFeed(startingVersion) and MERGEs incrementally. Facts use temporal joins on validity ranges.

Concepts covered:

  • SCD Type 1 vs Type 2: Type 1 overwrites (no history); Type 2 keeps every version with valid-from/to for point-in-time accuracy.
  • Change Data Feed (CDF): delta.enableChangeDataFeed records row-level inserts/updates/deletes so downstream reads only what changed.
  • MERGE (close + insert): On a change, MERGE expires the current row (end date, is_current=false) and inserts a new current row.
  • Point-in-time joins: Facts join the dimension version valid at each event's timestamp for historically-correct reporting.
  • Incremental gold: Reading Silver's CDF, only changed rows are MERGEd into Gold — no full recompute.

Implementation steps:

  1. Enable CDF on the Silver dimension.
  2. MERGE changes: close prior rows, insert new current rows (SCD2).
  3. Read CDF (readChangeFeed, startingVersion) downstream.
  4. MERGE only changed rows into Gold aggregates.
  5. Implement point-in-time fact→dim joins on valid-from/to.

Outcomes:

  • Full, auditable dimension history.
  • Efficient incremental Gold updates.
  • Historically-correct point-in-time reporting.

Stack: Delta Lake, Change Data Feed, MERGE

Point-in-time-correct reporting is essential for audited insurance analytics.

3. Large-table performance tuning

Goal: Make a multi-billion-row premium fact fast for filtered queries and MERGE.

Architecture & data model: A multi-billion-row premium fact tuned via OPTIMIZE+ZORDER (or liquid clustering) on policy/date/region, deletion vectors enabled, sensible partitioning — validated in the Spark UI.

Concepts covered:

  • OPTIMIZE / ZORDER: Compacts small files and co-locates data by filter/join keys so queries skip irrelevant files.
  • Liquid clustering: Maintains clustering on chosen keys without rigid partition directories, adapting to evolving writes.
  • Deletion vectors: Mark changed/removed rows without rewriting whole files, greatly speeding UPDATE/DELETE/MERGE.
  • Partitioning strategy: Partition on low-cardinality columns (e.g., date); avoid high-cardinality partitions that create tiny files.
  • File sizing / small-file problem: Many tiny files slow reads/metadata; compaction restores healthy file sizes.

Implementation steps:

  1. Diagnose small files/skew via DESCRIBE DETAIL and Spark UI shuffle metrics.
  2. OPTIMIZE with ZORDER on common filter/join keys (or enable liquid clustering).
  3. Enable deletion vectors for fast updates.
  4. Right-size partitioning; avoid high-cardinality partition columns.
  5. Benchmark query and MERGE runtimes before/after.

Outcomes:

  • Large reductions in files scanned and query latency.
  • Faster MERGE/UPDATE with less write amplification.
  • Documented before/after performance gains.

Stack: Delta Lake, OPTIMIZE / ZORDER, Spark UI

Mirrors re-engineering heavy reports for performance — a career signature.

4. Row/column security & PII governance

Goal: Ensure analysts only see permitted rows and masked PII on shared tables.

Architecture & data model: Shared Gold tables governed by Unity Catalog row filters + column masks; dynamic views for legacy paths; GDPR delete flow = DELETE → CDF propagation → VACUUM after retention.

Concepts covered:

  • Unity Catalog row filters: A function returning a boolean per row restricts which rows each user/group can query.
  • Column masks: Functions that redact sensitive columns unless the user is in an authorized group.
  • Dynamic views: Views using current_user()/is_account_group_member() to filter rows and mask columns without duplicating data.
  • PII handling: Identify and mask/tokenize personal data (names, IDs) before analysts or logs see it.
  • VACUUM for compliant deletes: After DELETE (and CDF propagation), VACUUM physically removes files past retention to satisfy erasure requests.

Implementation steps:

  1. Create a row-filter function (e.g., by region) and attach to the table.
  2. Add column-mask functions for PII keyed on group membership.
  3. Provide a dynamic view fallback where needed.
  4. Implement compliant delete: DELETE + downstream CDF removal + VACUUM.
  5. Audit access and lineage in Unity Catalog.

Outcomes:

  • Row/column-level security without data duplication.
  • Auditable, compliant handling of PII and erasure.
  • Least-privilege access across teams.

Stack: Unity Catalog, Dynamic views, Delta Lake

Governance and PII control are non-negotiable on regulated insurance data.

5. CI/CD deployment with Databricks Asset Bundles

Goal: Promote the pipeline across dev → staging → prod as tested, version-controlled code.

Architecture & data model: Git repo with the pipeline + tests; CI runs tests on PRs; a Databricks Asset Bundle deploys jobs/pipelines to dev→staging→prod with per-target variables; monitoring/alerts in place.

Concepts covered:

  • Databricks Asset Bundles: Declarative YAML defining jobs, DLT pipelines, and config with per-target variables for consistent deploys.
  • Multi-task job orchestration: A dependency DAG of tasks with retries and shared clusters, deployed as code.
  • Unit/integration testing: Unit tests on transformation functions plus integration tests on sample data, run in CI.
  • Monitoring & logging: Alerting on failed/long runs and per-run data-quality metrics for observability.
  • Environment parameterization: Per-target variables (catalog/paths) so one codebase runs in dev, staging, and prod.

Implementation steps:

  1. Author the bundle (databricks.yml) with resources and target variables.
  2. Write unit tests for transforms and an integration test on sample data.
  3. Configure CI to run tests on PRs and block merges on failure.
  4. Deploy the bundle per environment on merge.
  5. Add alerts on run failures/duration and track quality metrics.

Outcomes:

  • Repeatable, low-risk promotion across environments.
  • Regressions caught before production.
  • Observable, auditable deployments.

Stack: Asset Bundles, Git/CI, Databricks Jobs

Production-grade delivery discipline expected of a senior/lead engineer.

Practice questions (100)

1. You must propagate only the rows that changed in a Silver table to a Gold table without recomputing everything. What Delta feature enables this most efficiently?

  • A. Time travel
  • B. Change Data Feed (CDF) ✓
  • C. VACUUM
  • D. Deep clone

Explanation: Change Data Feed (delta.enableChangeDataFeed=true) records row-level changes so downstream jobs can read just the inserts/updates/deletes via readChangeFeed — enabling incremental propagation without full reprocessing.

2. Which SCD type preserves full history by adding a new row for each change with validity columns?

  • A. Type 0
  • B. Type 1
  • C. Type 2 ✓
  • D. Type 3

Explanation: SCD Type 2 inserts a new record for each change and marks the previous record as expired (via end-date/is_current columns), preserving complete history. Type 1 overwrites the value, keeping no history.

3. In Structured Streaming, what is the purpose of a watermark?

  • A. To encrypt streaming data
  • B. To bound state and handle late-arriving data in aggregations ✓
  • C. To compress checkpoints
  • D. To parallelize the driver

Explanation: withWatermark defines how late data can arrive before being dropped, which lets the engine bound the state it retains for windowed aggregations and stream-stream joins — preventing unbounded state growth.

4. What does the checkpointLocation provide to a Structured Streaming query?

  • A. A cache of the source data
  • B. Offset and state tracking for fault tolerance and exactly-once processing ✓
  • C. A backup of the cluster configuration
  • D. Compression of output files

Explanation: The checkpoint stores progress (source offsets) and any streaming state, so a restarted query resumes exactly where it left off — the basis for fault tolerance and exactly-once semantics.

5. Which streaming trigger processes all currently available data and then stops?

  • A. processingTime='0 seconds'
  • B. continuous
  • C. availableNow ✓
  • D. once='true' with backpressure

Explanation: Trigger.AvailableNow processes all data available at query start (in multiple micro-batches if needed) and then stops — ideal for scheduled incremental batch jobs on streaming sources. (It supersedes the older Trigger.Once.)

6. How do you implement column masking so non-privileged users see redacted values?

  • A. Store two copies of the table
  • B. A dynamic view using current_user()/is_account_group_member() logic ✓
  • C. VACUUM with a filter
  • D. Partition the table by user

Explanation: A dynamic view can conditionally mask columns or filter rows based on the querying identity (current_user(), is_account_group_member('...')), giving fine-grained access control without duplicating data. Unity Catalog also offers native column masks/row filters.

7. Which technique co-locates related data in the same files to skip irrelevant data during reads?

  • A. VACUUM
  • B. ZORDER BY ✓
  • C. REFRESH TABLE
  • D. CACHE TABLE

Explanation: OPTIMIZE ... ZORDER BY (col) clusters rows with similar values of the chosen column(s) into the same files, improving data-skipping for queries that filter on those columns.

8. What is a key advantage of Databricks Asset Bundles?

  • A. They compress Delta files
  • B. They define and deploy Databricks projects (jobs, pipelines, config) as code for CI/CD ✓
  • C. They replace Unity Catalog
  • D. They auto-tune Spark shuffles

Explanation: Databricks Asset Bundles (DABs) package a project's resources — jobs, DLT pipelines, notebooks, and configuration — as declarative YAML so they can be version-controlled and deployed consistently across environments via CI/CD.

9. A MERGE is running slowly on a large target table. Which change most directly reduces the data scanned?

  • A. Increasing the driver memory only
  • B. Adding a selective condition on partition/ZORDER columns so fewer files match ✓
  • C. Disabling the transaction log
  • D. Converting the table to CSV

Explanation: MERGE performance depends on how many target files must be read and rewritten. Filtering on partition columns and ZORDER-ing on the merge keys enables data-skipping so far fewer files are touched. Disabling the log isn't possible for Delta.

10. VACUUM with a retention of 0 hours is generally discouraged because it can:

  • A. Delete the schema
  • B. Break concurrent readers and disable time travel by removing still-needed files ✓
  • C. Duplicate the data
  • D. Corrupt the Parquet footer

Explanation: VACUUM removes files no longer in the latest version. Setting retention too low can delete files still needed by in-flight readers or for time travel, causing failures. Databricks enforces a safety check unless explicitly overridden.

11. Which read pattern lets you consume only new changes from a Delta table's change feed starting at a version?

  • A. spark.read.format('delta').load(path)
  • B. spark.read.option('readChangeFeed','true').option('startingVersion', n) ✓
  • C. spark.readStream.format('parquet')
  • D. COPY INTO with FORCE

Explanation: Reading with option('readChangeFeed','true') and startingVersion/startingTimestamp returns the row-level change events (with _change_type) from that point forward, provided CDF is enabled on the table.

12. For a stream-static join enriching a stream with a Delta dimension table, what is true?

  • A. The static side is re-read on each micro-batch, picking up updates ✓
  • B. The static side is read once and never refreshed
  • C. It requires two checkpoints
  • D. It is not supported in Structured Streaming

Explanation: In a stream-static join, the static Delta table is re-resolved on each micro-batch, so newer versions of the dimension are reflected in subsequent batches — a common enrichment pattern.

13. Which storage optimization physically removes rows marked for deletion and rewrites files?

  • A. A soft delete via DELETE only
  • B. OPTIMIZE / REORG (purge) after deletes ✓
  • C. VACUUM immediately
  • D. Time travel

Explanation: DELETE marks rows as removed in new files but old files linger until compaction/reorg and VACUUM purge them. OPTIMIZE (and REORG ... APPLY (PURGE) for deletion vectors) rewrites files to physically consolidate changes.

14. Deletion vectors in Delta improve DELETE/UPDATE performance by:

  • A. Encrypting deleted rows
  • B. Marking deleted rows in a side file instead of immediately rewriting data files ✓
  • C. Dropping the table
  • D. Disabling the transaction log

Explanation: Deletion vectors record which rows are removed without rewriting whole Parquet files on each DELETE/UPDATE/MERGE, greatly speeding those operations; a later OPTIMIZE/REORG materializes the changes.

15. For an idempotent batch write that can safely retry without duplicates, you should:

  • A. Append blindly each run
  • B. Use MERGE on a key or foreachBatch with idempotent writes / txnAppId ✓
  • C. Disable checkpoints
  • D. Use CSV output

Explanation: Idempotency is achieved by keying writes (MERGE on a business/primary key) or using streaming idempotent-write features (txnAppId/txnVersion in foreachBatch), so a retried batch doesn't create duplicates.

16. When aggregating a stream with a window, what prevents unbounded state growth?

  • A. Caching
  • B. A watermark that expires old state ✓
  • C. Broadcast joins
  • D. ZORDER

Explanation: A watermark tells the engine how late data may be, allowing it to finalize windows and drop state older than the threshold — bounding memory for windowed aggregations and stream-stream joins.

17. Which output mode emits only rows that changed for a streaming aggregation with a watermark?

  • A. complete
  • B. append
  • C. update ✓
  • D. overwrite

Explanation: update mode outputs only the rows whose aggregate changed in the trigger. complete rewrites the entire result each time; append only emits finalized rows (valid for aggregations with a watermark once windows close).

18. A Type 2 SCD MERGE must, for a changed record:

  • A. Overwrite the existing row
  • B. Expire (close) the current row and insert a new current row ✓
  • C. Delete the dimension
  • D. Do nothing

Explanation: SCD Type 2 preserves history: on a change, the current row is closed (end date set / is_current=false) and a new row with the new values and open validity is inserted — typically via a two-step MERGE.

19. Which is the recommended way to schedule and interconnect dependent notebooks/pipelines in production?

  • A. Cron on a single notebook
  • B. A multi-task Databricks Job with task dependencies ✓
  • C. Manual runs
  • D. A dashboard

Explanation: Multi-task Jobs let you define a DAG of tasks (notebooks, DLT pipelines, scripts) with dependencies, retries, and shared job clusters — the standard production orchestration on Databricks.

20. To diagnose a slow stage caused by data skew, the Spark UI would most likely show:

  • A. All tasks finishing simultaneously
  • B. A few tasks taking far longer / processing far more data than the rest ✓
  • C. No shuffle read
  • D. Zero input rows

Explanation: Skew appears as a small number of straggler tasks handling disproportionately large partitions while others finish quickly. AQE skew handling or salting the key mitigates it.

21. Which approach best secures PII columns so only authorized groups see raw values?

  • A. Store PII in file names
  • B. Column masking via a dynamic view / Unity Catalog column mask keyed on group membership ✓
  • C. Broadcast the column
  • D. Increase retention

Explanation: A dynamic view or Unity Catalog column-mask function returns masked values unless is_account_group_member('authorized') is true — enforcing column-level security without duplicating data.

22. What does enabling Change Data Feed add to a Delta table's writes?

  • A. Nothing observable
  • B. Recorded row-level change events readable later via readChangeFeed ✓
  • C. Automatic ZORDER
  • D. A synthetic key

Explanation: With delta.enableChangeDataFeed=true, Delta records row-level changes (with _change_type) so downstream consumers can read exactly what was inserted/updated/deleted from a given version.

23. A stream reading from a Delta table with frequent small commits performs poorly downstream. A good remedy is to:

  • A. Disable the checkpoint
  • B. Periodically OPTIMIZE the source and/or tune trigger interval and maxFilesPerTrigger ✓
  • C. Convert to CSV
  • D. Remove the watermark

Explanation: Many tiny files hurt throughput. Compacting with OPTIMIZE and controlling ingestion rate (maxFilesPerTrigger / trigger interval) balances latency against efficiency for the downstream stream.

24. Which testing practice is most appropriate for validating a transformation function in a pipeline?

  • A. Only manual visual checks in production
  • B. Unit tests on the function with sample inputs/expected outputs, plus integration tests on a small dataset ✓
  • C. No testing — Delta guarantees correctness
  • D. Testing only after go-live

Explanation: Reliable pipelines use unit tests for pure transformation logic (deterministic input→output) and integration tests over representative sample data, ideally wired into CI before deployment.

25. Deep clone vs shallow clone of a Delta table: a shallow clone:

  • A. Copies all data files
  • B. Copies only metadata and references the source's files (fast, space-efficient) ✓
  • C. Encrypts the table
  • D. Is not supported

Explanation: A shallow clone copies just the metadata and points to the source's existing data files — quick and cheap for testing. A deep clone also copies the data, making an independent full copy.

26. To make a streaming foreachBatch write idempotent across retries, you set:

  • A. A larger cluster
  • B. txnAppId and txnVersion (or use MERGE) so replays are deduplicated ✓
  • C. CSV output
  • D. A shorter watermark

Explanation: Providing a consistent txnAppId/txnVersion (or writing via MERGE on a key) lets Delta recognize and skip duplicate batch writes on retry, guaranteeing exactly-once effects.

27. Which is the best strategy to handle late-arriving dimension updates in a fact-dimension join stream?

  • A. Ignore late data
  • B. Use a stream-static join that re-reads the dimension each micro-batch, or maintain SCD Type 2 ✓
  • C. Disable checkpoints
  • D. Convert to CSV

Explanation: A stream-static join re-resolves the dimension each batch (reflecting updates), and SCD Type 2 preserves historical accuracy for point-in-time correctness — appropriate depending on requirements.

28. OPTIMIZE with ZORDER is most beneficial when queries frequently:

  • A. Select all columns with no filter
  • B. Filter/join on specific high-selectivity columns ✓
  • C. Only count rows
  • D. Write data

Explanation: ZORDER co-locates data by the chosen columns so queries filtering on them read far fewer files (better data-skipping). It helps read-heavy, selective filter/join workloads, not full scans.

29. Which metadata helps you audit who changed a table and when?

  • A. DESCRIBE DETAIL
  • B. DESCRIBE HISTORY ✓
  • C. SHOW TABLES
  • D. EXPLAIN

Explanation: DESCRIBE HISTORY lists each version with the operation, timestamp, and user — the primary audit trail for a Delta table. DESCRIBE DETAIL shows table-level metadata like size and location.

30. A pipeline must reprocess all historical data after a logic fix. The cleanest streaming approach is to:

  • A. Edit files manually
  • B. Use a new checkpoint location to reprocess from the beginning ✓
  • C. Delete the target schema
  • D. Lower the watermark to zero

Explanation: Pointing the stream at a fresh checkpoint (and typically a full-refresh target) reprocesses from the source's start, since the checkpoint tracks progress. Reusing the old checkpoint would resume, not replay.

31. Which approach limits how much data a single micro-batch ingests to control load?

  • A. maxFilesPerTrigger / maxBytesPerTrigger ✓
  • B. ZORDER
  • C. VACUUM
  • D. QUALIFY

Explanation: Rate limits like maxFilesPerTrigger (Auto Loader/Delta) or maxBytesPerTrigger cap per-batch input, smoothing throughput and preventing overwhelming downstream systems.

32. Row-level security in Unity Catalog is implemented with:

  • A. A separate table per user
  • B. A row filter function applied to the table ✓
  • C. VACUUM
  • D. A bookmark

Explanation: Unity Catalog supports row filters (a function returning a boolean per row) and column masks, applied to a table so users see only permitted rows/values — centrally governed.

33. When designing bronze ingestion, capturing ingest metadata (file name, load timestamp) is valuable because it:

  • A. Is required by Spark
  • B. Aids lineage, debugging, and incremental/idempotent reprocessing ✓
  • C. Encrypts the data
  • D. Reduces file size

Explanation: Recording source file/path and ingestion time (e.g., input_file_name(), current_timestamp()) supports lineage, troubleshooting, and reprocessing logic in the bronze layer.

34. Which is TRUE about Auto Loader file notification mode vs directory listing mode?

  • A. They are identical
  • B. Notification mode uses cloud events to discover files, scaling better for very high file volumes ✓
  • C. Listing mode is always faster
  • D. Notification mode cannot use checkpoints

Explanation: Directory listing enumerates the path; file-notification mode subscribes to cloud storage events (queues/notifications), scaling more efficiently when directories contain huge numbers of files.

35. To deploy the same pipeline across dev/staging/prod with environment-specific config, use:

  • A. Copy-paste notebooks
  • B. Databricks Asset Bundles with per-target variables ✓
  • C. Manual cluster edits
  • D. A single shared notebook

Explanation: Asset Bundles define resources and per-target (environment) variables in code, enabling consistent, parameterized CI/CD deployments across dev/staging/prod.

36. A gold aggregate must always reflect corrected upstream data. Using Change Data Feed on silver lets you:

  • A. Recompute the entire gold table each run
  • B. Incrementally apply only changed rows to the gold aggregate ✓
  • C. Disable governance
  • D. Avoid checkpoints entirely

Explanation: Reading silver's CDF gives just the inserts/updates/deletes, so the gold layer can be updated incrementally (via MERGE) rather than fully recomputed — efficient and correct.

37. Which Spark UI signal most directly indicates excessive shuffle?

  • A. Low input size
  • B. Large 'Shuffle Read/Write' bytes across stages ✓
  • C. Zero tasks
  • D. High cache hit rate

Explanation: Big Shuffle Read/Write metrics reveal costly data movement. Reducing wide operations, broadcasting small tables, and tuning partitions (or AQE) mitigate it.

38. For GDPR-style deletes on a Delta table, you must also eventually run:

  • A. OPTIMIZE only
  • B. VACUUM (after retention) to physically remove the underlying files ✓
  • C. REFRESH
  • D. ANALYZE

Explanation: DELETE removes rows logically, but the old files persist for time travel until VACUUM purges them past the retention window — required to physically erase data for compliance.

39. Auto Optimize (optimizeWrite + autoCompact) helps by:

  • A. Encrypting data
  • B. Producing better-sized files during writes to reduce the small-file problem ✓
  • C. Disabling the log
  • D. Removing partitions

Explanation: Auto Optimize combines optimized writes (right-sized files) and auto compaction (merging small files after writes), mitigating small-file issues without a separate OPTIMIZE job.

40. For exactly-once delivery to a downstream system from a stream, you should:
